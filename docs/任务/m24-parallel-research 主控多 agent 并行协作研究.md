# T15：主控拆分任务后的多 agent 并行协作研究

2026-09-23。交付研究结论，不实施正式功能。本轮未创建真实 agent，未运行真实任务推进；验证只用了自动清理的合成 Git 仓库与合成看板状态。

## 研究范围与依据

- 研究的是**一件顶层任务内部**的并行，不改变 drover 顶层队列串行推进。
- 已安装的 `~/.agents/skills/corral-dispatch/SKILL.md` 与 corral 仓库的 `corral-dispatch-skill/SKILL.md` 字节一致；本机 `corral --version` 报 `0.1.0`、契约版本 `1`。只读了 `docs/CONTRACT.md`，没有读 corral 源码或状态目录。
- drover 的现行依据是本仓库 `AGENTS.md`、`docs/ROADMAP.md`、`bin/drover-board`。没有修改 corral、corral-dispatch、ROADMAP 或业务代码。

## 现有能力与实际缺口

| 环节 | 已有能力 | 边界 |
|---|---|---|
| 触发与拆分判断 | 项目 `AGENTS.md` 的“主控分派”条款让主控在用户说开始后按 corral-dispatch 办；项目模板还记录了一次“两项小功能 → 两份任务文件”的试跑。技能第 1 节给出先定地基、检查文件重叠、写接口约定等拆分原则。 | **corral 不会判断任务；corral-dispatch 也没有自动识别可并行子任务的程序或保证。** 主控模型须读顶层目标、项目设计和代码后自行判断。技能没有要求每件顶层任务都显式给出“拆/不拆及理由”；模板试跑也不能证明复杂、隐含依赖的任务会被拆对。这是本研究最重要的未验证点。 |
| 拆分与并行 | corral-dispatch 第 1 节已规定：公共数据模型和接口先定，文件范围重叠则串行，独立部分分别用 agent、分支和 worktree，并预先指定集成负责人；有集成关系的两半先验组合结果再合入 main。 | 架构级决定要交用户；被委派的 agent 不再下派。主控负责整个分解与协调。 |
| 通信与跟踪 | corral 契约提供逐个 agent 的 `start`、`status`、`wait`、`reply`、`send`、`ls`。任务文件记录工作范围、接口和完成证据。 | 契约没有顶层任务 ID、子任务关系、开发/审查角色或任务完成状态。`idle` 只是回合结束；`send --after` 连 blocked、退出和超时也会继续尝试送话，不能充当“依赖任务已完成”的闸门。 |
| 审查与返工 | corral-dispatch 第 5–7 节要求主控审查每件活；高风险项才独立交叉审查。审查者读 detached worktree，返工交回原开发 agent，复核后再集成、合并、清理。 | 主控仍须逐件核实回复、提交和测试；独立审查可与另一子任务开发并行，但最终组合结果还须验收。 |
| 顶层完成 | drover 仍只送一条顶层任务。`task_branches()` 检查包含派发起点的本地分支是否都已在 main；`find_done_mark()` 只认顶层范围内的收尾空提交。 | 分支门只说明 Git 归并，不说明各子任务的审查或验收是否完成。只有主控能作最终判断并打收尾记号。 |
| 看板 | `crew_of()` 按 corral `ls` 的 cwd 和 Git worktree 路径列出同仓库 agent；当前卡片显示正文、Git 进展、判据，corral board 负责更细的 agent 观察。 | `crew` 不是本顶层任务的成员表，也不区分开发/审查；没有可靠的子任务 ID、依赖、审查轮次或完成阶段。不能从 agent 的 `idle` 或分支已合并推断子任务完成。 |

ROADMAP 已明确把 drover 定位为任务看板，并指出 corral board 承担 agent 状态观察；新增子任务视图前要先证明现有两块看板仍不能回答用户的问题。

corral-dispatch 第 1 节同时要求“派新活之前确认上一件已收尾”并明确允许同一件事拆成有集成关系的并行部分。这里把前者理解为**不能让新的顶层任务压过未收尾的上一件**，兄弟子任务仍属同一顶层任务；这是从同节上下文作出的解释，真实试行时应在任务文件里把顶层身份写清，避免把下一条队列任务误当兄弟任务。

### 主控如何知道要不要拆

现有机制的答案是“主控依据任务和项目上下文作判断”，不是 corral 返回拆分方案。一个可检查的判断顺序是：先列顶层验收目标和产物，再找可分别验收的工作包；画出依赖，检查是否共享未定的数据模型/接口或同一批文件；只有契约已定、修改范围可隔离、集成负责人明确，而且并行收益值得协调成本时才同时派出。否则先做地基或保持串行。**这段是研究建议，不是技能已经强制执行的步骤。**

本轮只检查了技能文本、项目开关和已有模板记录，没有让一个真实主控仅凭含糊的顶层任务做盲拆，因此不能说它会稳定地发现并行机会，也不能说它会在不该拆时自动克制。真实试行前应先做不启动 agent 的拆分演练：给主控若干只有顶层目标的任务，请它写“拆/不拆、依赖、文件边界、集成办法和不确定点”，由人核对判断质量。

### 建议的分派前判断契约（供用户裁定，尚未写入 AGENTS）

**输入**是用户的一件顶层任务、验收要求、项目设计文档和相关代码。主控先查清受影响模块与文件，列出候选工作包及依赖图，再比较并行后可能缩短的关键路径与接口协调、审查、集成成本。模型负责判断与解释；可机械核对的文件范围重叠、共同起点、接口字段和验收责任作为出发前的检查，不把文件数或关键词当成自动拆分算法。

**输出**必须先给一个有依据的选择，再派 agent：

| 判断 | 采用条件 | 下一步 |
|---|---|---|
| 单任务 | 一个紧耦合的产物，或多块工作反复修改同一处、拆开后难独立验收，协调成本超过收益。 | 一个开发 agent 承担，主控照常审查。 |
| 先串行地基，再并行 | 确有可独立的后续工作，但共享模型、接口或架构尚未定。 | 先完成公共约定；属于架构级选择时问用户，然后再拆后续任务。 |
| 立即并行 | 至少两个可独立验收的结果；接口已定、文件责任可隔离、依赖与集成负责人明确，预计能缩短关键路径。 | 主控写各自任务文件和共同约定，再同时派出。 |

无论选哪一项，都记录候选子任务、依赖、预计改动文件、接口、验收与集成责任，以及不并行或并行的理由。对可能互相覆盖的文件、隐藏依赖或不清楚的验收先做反向检查；证据不足时保守地选单任务或先做地基，不能为了凑 agent 数量而拆。常规执行方式由主控决定，已定设计之外的架构取舍才交用户。

这应先作为**项目级主控规则**试验，避免为了 drover 改 corral/corral-dispatch。只写一句“尽量并行”不足以实现上述判断：还需用含单任务、可并行、先地基三类样本的规划演练，检查误拆、漏拆和理由是否与代码事实一致。模板里已有的“两项小功能”试跑只证明明显可拆时主控曾拆出两份任务，不能代替这个评估。若以后要让所有项目默认具备此规则，才另行讨论通用技能边界。

## 可用现有流程试行的组织方式（建议，尚未实施）

```text
顶层任务
  ├─ 公共接口/数据约定（有争议时先由用户裁定）
  ├─ 子任务 A ─┐
  └─ 子任务 B ─┴─ 集成验收 ─ 主控最终审查 ─ 合入 main、清理、收尾
                    └─ 高风险部分按需交叉审查；问题回原开发 agent 返工
```

1. 主控先列依赖和文件范围。输入/输出契约能事先写清、文件修改范围基本不重叠、每部分有独立可查的结果，才同时派出。共享模型未定、同文件反复改动或一方必须等另一方结果时先串行。
2. 每个子任务沿用现有任务文件、分支、worktree；同一份接口约定写进相关任务文件，并注明另一方的文件范围、依赖和集成负责人。主控用一份顶层工作清单记“谁负责什么、证据在哪、下一步依赖谁”；这是主控自己的协作记录，不供 drover 解析自然语言。
3. 主控分别核对 `status`、`reply`、提交和任务文件。`wait`/`--after` 只辅助获知回合变化；收到 `DONE` 也仍要审查。可以在 B 开发时审查已稳定的 A；需要返工就送回 A，保持原 worktree 和 agent。
4. 集成负责人在自己的分支纳入另一已稳定分支，执行组合验收；主控复核组合结果后再合入 main。有集成关系的 worktree 在组合验收前都保留，以便返工。最后清理分支/worktree、按项目约定留下**一条顶层收尾记号**。

此方式不要求 corral 或 drover 新增命令，也不让被委派者继续下派。它的成本是主控需要同时维护多个任务文件、状态和审查结论；实际节省多少时间，本轮合成验证无法测量。

## 合成验证

全部在 `tempfile.TemporaryDirectory()` 内执行，退出时自动清理；通过 `runpy.run_path('bin/drover-board')` 调用当前 `criteria()`、`find_done_mark()` 和 `add_waits()`，没有调用真实 corral 或改真实 queue/tasks.state。

| 场景 | 实测结果 | 说明 |
|---|---|---|
| 两个分支从同一任务起点建立，只把 A 合入 main | 分支门为假，理由列出未合入的 B；收尾记号为假 | 一半完成不会因 main 已前进而放过顶层任务。 |
| A、B 都合入，但尚未打记号 | 分支门为真，收尾记号为假 | Git 归并本身不等于主控收尾。 |
| 两者合入后再打单亲、空的 `收尾:` 提交 | 分支门与收尾记号都为真 | 现有顶层完成机制兼容两个子分支。 |
| B 先合入集成负责人 A 的分支，组合文件在 A；之后只把 A 合入 main | 合入前门列出 A、B；合入后两个分支都成为 main 祖先，门为真 | 支持“先组合验收、再一次合入 main”的路径。 |
| 主控 `idle` 121 秒，合成开发 agent 仍 `working`，main 尚未前进 | `add_waits()` 仍设 `needs_me=true` 并产生“主控空闲着，但这件活的判据还没满足”的 `STOP` 提示 | 这是现有提示的宽松启发式，不会触发完成或派发；并行开发时可能把正常等待显示成需要用户查看。ROADMAP 已承认 `idle` 含义模糊，本轮仅记录，不改既定规则。 |

这些实验只验证当前 Git 判据和看板数据路径；没有真实多 agent 同时工作的耗时、冲突率、审查质量或终端体验证据。另须遵守已有分支门限制：本次分支应从包含顶层 `base_sha` 的提交建立；从更早基点建立的分支可能被排除。

## 方案取舍

| 方案 | 能解决什么 | 代价与建议 |
|---|---|---|
| A. 先做顶层任务的只读拆分演练，再用现有流程做一次真实但受控的双子任务试行 | 前一步验证主控能否发现适当的并行边界，后一步验证协调、返工与集成是否真比串行顺畅；drover 保持顶层队列和判据。 | **建议下一步选择**，但须由用户另行选定场景并授权试行；本 T15 不启动真实 agent。记录拆分判断、协调时间、冲突、返工和看板观察缺口。 |
| B. 如试行暴露协调遗漏，给目标项目的任务文件补一份简短的顶层依赖/负责人清单 | 让主控与用户看到明确责任、依赖和验收位置。 | 先作为主控文档习惯，不修改 corral-dispatch 技能，不要求 drover 解析。若要固定为项目规则，应再核对已有设计。 |
| C. 如用户确需 drover 展示子任务阶段，再单独设计稳定的数据来源和显示范围 | 可能展示“子任务—agent—审查”关系。 | 目前 `ls/status`、分支和自由文本任务文件均不能可靠提供完整关系。强制主控为 drover 写新字段会触及“不得为 drover 多做事”的硬边界；须先取得设计裁定，不能直接实现。 |

把 agent 生命周期或子任务调度移进 drover、为了 drover 给 corral 增字段/命令、让 drover 解析审查结论，均越过现有边界，本轮不作为默认方案。

## 需要用户决定的事

1. 是否先用若干顶层任务做只读拆分演练；若判断质量可接受，是否把上述三态判断契约写入项目 AGENTS，并挑一件真实任务受控试行。这样先检验主控的判断，再检验派出后的执行。
2. 试行阶段是否暂用现有 drover 看板的顶层进展/agent 列表，加 corral board 和主控工作清单观察子任务；若这不足以看清全局，再单独定子任务数据来源与看板设计。
3. 并行期间主控 `idle` 且开发 agent 仍工作时，现有 `STOP/needs_me` 是否可接受为“去看看”的宽提示；如果不接受，应另立显示规则修正任务，保持完成判据独立。
