- **现有测试看不到这次崩溃**：它们只走 `view_model` / `detail_lines`，不到绘制层。审查者植入「每份有效记录的 `why` 追加 NUL」后 **8 个测试仍全绿**——这是真盲区。
- **深层嵌套 JSON 的 `RecursionError`**：`/usr/bin/python3`（3.9.6）会抛，本机默认 3.14.7 不抛。**不能拿本机解释器不报错当保护成立**——仓库只要求 Python 3。

采纳改法：读取边界处理 `RecursionError`；校验解码后的字符串能安全进显示（至少拒绝 / 转义 NUL），不能只认「是 str」；**回归要验到绘制边界**。不要用包住整个看板的宽泛 `except` 冒充修复。

### 2. 显示记录发布失败会中断完成判断 —— **必须改，采纳**

同意，而且这是**设计边界被破坏**，不只是健壮性问题。ROADMAP 写死「这个文件只喂看板，绝不参与任何判断」，而现在把 `.check-result` 放成一个目录，`os.replace` 抛 `IsADirectoryError`，`drover done` 就退出 1、`done` 事件根本不写——**显示文件的发布状态成了完成判断的新前提**。

采纳改法：发布做成**可失败的旁路**，I/O 错误报诊断但不动真实判据的返回值和队列推进。加「marker 路径异常但 `tasks.state` 可写」的对照用例，断言完成事件和退出码不变。

### 3. 隔离守线有五个盲区 —— **必须改，采纳**

主控上一轮只发现了其中一条（`except Exception: pass` 吞掉 `AssertionError`），审查者补齐了另外四条，**五项植入全部退出 0**：`Path().read_bytes()` 走 `io.open` 不经 `builtins.open`、`os.open`+`os.read`、`subprocess cat`、以及 `check_done()` 是**另一个 Python 进程根本不继承父进程的 mock**。

我上一轮在审查结论里说这条守线「从机制上禁止读取」，**这个说法不准确**，按审查者的口径修正：它只封住了同进程的 `builtins.open`。

采纳改法：把读取尝试记进独立计数器、调用返回后断言为零（生产代码吞异常也藏不掉）；把同进程的 `check_done()` 纳入守线；对 `builtins.open` / `io.open` / `os.open` 统一观察并规范化路径。**子进程 `cat` 那条不要求封住**——按审查者说的，**明确写出守线的覆盖范围**，不要再宣称「从机制上禁止」。不必搭通用文件访问沙箱。

### 4. 限制读取量与理由长度 —— 建议改，**采纳**

2 MiB 的 `why` 实测能完整进内存。只在这一处做有界读取、`why` 设上限，超限按坏记录降级。**不要顺带重构全局 `read()` 或排版函数。**

### 5. 明显在未来的时间 —— 建议改，**采纳**

`t = 现在 + 86400` 会显示成 `（0s 前跑的）`——**把坏时间伪装成刚跑过**，方向在危险那侧（人会以为刚验过）。采纳审查者的提醒：`collect()` 的 `NOW` 在采集开始时取，正常并发发布也可能稍晚，**不要简单拒绝所有 `t > NOW`**，要留采集偏差。

### 6. 按 `n == 3` 定位 —— 建议改，**采纳**

一行的事，且 `bin/drover:218` 已经是这么写的，两处统一。

### 7/8/9. 可以不改 —— 同意

审查者做了 6 轮并发实测（两个真实 `drover done` 同时跑，另一进程读 108 次），**没有半截 JSON、没有串写、正常结束无 tmp 残留**——同目录 `os.replace` 够用，不加锁不加 fsync。三键陈旧判定符合已定设计，只发布第一次合理。

**两条记欠账，本次不改**（审查者明确说不要求本次做）：

- **强杀进程会留下 `.check-result.<pid>.tmp`，没有清扫机制，会积累。** 看板不把它当核对记录，无害但会攒。
