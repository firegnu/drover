# T16：主控自主拆分与并行 agent 数量决策研究

2026-09-23。T15 的后续研究；不实施正式功能。本轮未启动开发或审查 agent，未操作真实任务推进。以下规划演练由主控根据只读项目资料和合成场景完成，不能当作多个独立模型的能力测评。

## 结论

用户只需交一件顶层任务。**拆分判断应由主控在派发前完成**：先找可独立验收的成果与依赖，再核对接口、文件所有权和组合验收，最后选择单路、先地基后并行或立即并行。并发数取“能明显缩短关键路径、且协调和审查负担仍可控的最小人数”，不是子任务数、文件数或固定上限。审查 agent 按错误代价单独决定，不能算作开发并发的默认配额。

现有项目 `AGENTS.md` 要求主控分派，模板的一次试跑说明明显可拆的任务能够触发；corral-dispatch 已写明地基先行、并行文件与接口边界、集成负责人、审查和收尾。**缺的是派发前必须给出有依据的拆/不拆判断、分阶段人数和反向检查的明确步骤与验证**；也尚未验证任意顶层任务都能稳定触发适当规划。corral 契约只有 agent 会话操作，不需要为此加命令或字段；drover 也不应承担语义规划或 agent 生命周期。建议先在本项目主控规则中小范围验证判断质量；若要跨项目默认生效，再另立 corral 仓库任务讨论修改通用技能。两者均未在 T16 实施。

## 规划演练：一条顶层任务如何决定人数

口径：`开发总数`是整件事创建的不同开发会话；`开发峰值`和`工作峰值`是同时实际工作的会话数，主控不计入。agent 可以为返工保留 worktree 而处于 idle，因此**活着的会话峰值可能大于工作峰值**；执行时要另报。独立审查会话只在风险要求时加，不能以每个候选工作包都配一位审查者为默认。

### A. 紧耦合小修：T10 `drover list` 异常字符崩溃

- 顶层输入仅是“修复 list 遇异常字符标题时崩溃”。候选包为输出调用点和定向测试；二者围绕 `bin/drover:cmd_list` 与同一输出契约，拆开要多一次接口交接，不能形成独立的用户成果。
- **判断：单路。** 一位开发 agent 同时负责代码与 `tests/list-output.py`，主控复跑并审查，无独立审查；开发总数 1、开发/工作峰值 1。历史 `491d7f6` 的生产改动只在 `bin/drover`，任务记录的独立审查结论为“不要”。这只是适合单路的证据，不证明所有小修都不能并行。

### B. 看似可拆、实际共享改动：T13 完整历史与局部滚动

- 顶层输入是“显示完整任务历史并支持历史区局部滚轮”。候选包：历史加载/批量统计、视口布局、滚轮命中、端到端验收。它们依次影响同一个 `bin/drover-board` 的 `task_view`、`draw`、`key_action` 及共用显示数据，验收必须验证整条路径。旧的五条截取取消后才暴露每条 Git 查询的性能依赖。
- **判断：单路并保留调查关口。** 一位开发 agent 先测量，再做显示和交互；性能方案若触及已定设计，先交用户决定。主控做组合验收；开发总数 1、峰值 1，无默认独立审查。历史 `b0a586e` 的唯一生产文件是 `bin/drover-board`，任务中曾因性能关口暂停并待用户批准，说明起始时硬拆“数据 agent + 界面 agent”容易返工。

### C. 先地基后两路：合成的“任务暂停原因同时进入命令行与看板”

- 顶层输入只写用户目标，假设要新增持久化事件字段。候选包/依赖：`事件语义与解析契约 → {CLI 操作, TUI 展示} → 组合验收`。当前 `bin/drover` 从 `bin/drover-board` 导入队列/事件解析，`task_fold` 在后者；字段、缺省值和旧事件兼容未定时，两端不能各自猜。该事件语义属于已定设计之外的候选变更，真实执行须先经用户裁定。
- **判断：先串行一位定契约，批准并落地后再两路。** 后续 CLI agent 只拥有 `bin/drover` 与命令测试，TUI agent 只拥有 `bin/drover-board` 的显示/输入与界面测试；共享字段及验收样本冻结在任务文件。指定 CLI agent 的集成分支纳入 TUI 成果做组合验收，主控复核。若暂停语义影响核心队列判据，再增一位独立审查者审组合 diff。开发总数 3、开发峰值 2；该审查者使委派总数 4，但安排在稳定集成后，工作峰值仍为 2。先期地基 agent 的 worktree 按项目规则收尾后再开下阶段；具体审查结论仍要按风险路由确认。

### D / D′. 相同目标、不同项目事实：合成的“新增搜索”

- **D：接口已批准。** 假设项目已经确定 `GET /search?q` 返回 `{ids: string[]}`，后端 `api/search.py`、前端 `web/Search.tsx` 及各自测试互不覆盖。候选包 `API 实现 ∥ UI 实现 → 联调`；API agent 负责集成，双方各自验收协议样本，主控审查组合行为。**立即两路**：开发总数 2、开发/工作峰值 2；第三位开发没有独立工作包。普通本地搜索无额外高风险事实时，不预留独立审查。
- **D′：接口未定。** 顶层目标文字完全相同，但存储模型、结果排序与返回字段尚无批准方案。候选包变成 `架构/接口裁定 → {API, UI} → 联调`。架构级选择先交用户；一位地基 agent 可以先调查和起草，不让两端猜协议。裁定后开发总数最多 3、开发峰值 2；若最终实现实际上集中在一处，则退回单路。**相同任务文本产生不同人数**，说明仅看关键词或“前后端”标签无法可靠决定并行。

### E. 三路确有收益：合成的三个独立适配器

- 假设用户只提一条顶层需求：“把已经批准的统一输入格式接入 A、B、C 三种独立来源”；三个适配器的输入/错误契约固定，各在独立文件及测试中工作，工作量相近，各能单独验收。候选包 `A ∥ B ∥ C → 集成回归`；指定 A 的开发 agent 汇总，主控核对三份适配器和组合结果。
- **判断：三路有条件成立。** 开发总数/峰值 3、无预设独立审查。若查明 C 很短、共享输入契约未定、文件所有权冲突或第三位的协调成本吃掉节省，则改为两路或先地基。这里的“三”来自三个实质独立且同量级的工作包，不是常数。

### F. 审查人数独立于开发人数：T14 安装 PATH 修复

- 顶层输入是“修复安装时把临时 PATH 写入后台 plist”。调查、最小实现、隔离安装验证围绕 `install.sh` 和 `tests/install.sh` 串行推进，文档需要反映已定行为；把调查和实施同时派出会让实现抢先采用未批准的 PATH 政策。
- **判断：一位开发，稳定 diff 后一位独立审查。** 开发总数 1，审查总数 1，工作峰值 1；开发会话为返工保留时，活着的会话峰值可达 2。历史 `a1b64fc` 证实生产仅改 `install.sh`，而任务按高风险安装/服务环境安排了独立审查。两位受委派 agent 不等于“两路并行开发”。

### 小规模核算与误判对照

为检查“派几位”是否符合依赖图，给各合成包赋**假设工作单位**，只按依赖与同时工作的席位数算最短工期；不含启动、协调和返工成本，也**不是实际小时数**。一次性 Python 枚举的输入为：A `修复3`；B `数据4→视口6→集成2`；C `契约3→{CLI4,TUI5}→集成2`；D `API8∥UI8→集成2`；D′ `契约3→{API8,UI8}→集成2`；E `三个适配器各6→集成2`；F `开发5→审查2→收尾1`。各包不可中断，前置包完成才可开始后续包，分别限定 1/2/3 个同时工作席位，结果如下：

| 场景 | 1 席位 | 2 席位 | 3 席位 | 对人数的约束 |
|---|---:|---:|---:|---|
| A 单个修复包 | 3 | 3 | 3 | 第二位无事可做。 |
| B 串行数据→视口→验收 | 12 | 12 | 12 | 工作包多也不代表并发宽度大。 |
| C 地基→CLI/TUI→集成 | 14 | 10 | 10 | 后段最多两路；第三位不能再缩短关键路径。 |
| D 稳定搜索 API/UI→联调 | 18 | 10 | 10 | 两路有明显潜力，第三位无收益。 |
| D′ 未定接口→API/UI→联调 | 21 | 13 | 13 | 相同目标增加先行依赖；不能提前两路猜接口。 |
| E 三个等量独立适配器→集成 | 20 | 14 | 8 | 第三位**可能**有意义，仍须比较协调成本。 |
| F 调查实施→独立审查→收尾 | 8 | 8 | 8 | 总共用到两类 agent，不产生开发并发。 |

这个核算只验证计划的依赖与人数算术，**没有验证真实主控在未知任务上的稳定判断率**，也没有测真实节时或 token 成本。固定“总用一个”会漏掉 D/E；固定“有三块就开三位”会误拆 B/C/F。D 与 D′ 是同一句目标的反例：准确决策必须读取已批准接口与代码事实。T15 的 Git 判据实验验证的是派发之后能否收尾，也不能填补这里的判断证据。

## 建议的派发前判断流程（待采纳，不是现行强制规则）

1. **明确输入与成果。** 读顶层目标、验收、项目设计和受影响代码；列出候选可独立验收成果，而不是先列 agent 名字。把架构级未决、数据权限和明确用户边界单独标出；已批准设计照办。
2. **画最小依赖图并反证拆分。** 逐包写前置条件、预计文件所有权、共享接口字段、测试责任和集成负责人。问“最强的不并行理由是什么”：同一文件反复改、共用未定接口、验收只能整体做、关键路径没有缩短或审查/合并成本偏高，任何一条成立就串行该部分。文件交叉只是信号，不能只按路径机械判断。
3. **比较少量可行波次。** 从单路开始，增加一位只有在产生新可启动且可独立验收的工作包、预计关键路径节省超过额外协调/集成成本时才接受。记录开发会话总数、每阶段同时工作的开发人数、独立审查会话数、全体工作峰值与可能保留的活会话峰值；估时用区间并标注低置信度，不假装精确优化。
4. **决定审查与派发。** 主控始终审每包；数据模型、并发、隐私、安全、核心规则及高代价安装/迁移按现行路由和第 6 节判断独立审查。审查从稳定 diff 开始，复杂接口还应审组合结果；不是每加一位开发就配一位 reviewer。若无架构级未决，常规拆分与人数由主控自行决定，不要求用户重复批准。
5. **执行时重规划。** 记录“未启动/进行中/阻塞/待审/返工/待集成/完成”与负责人、依赖、下一次检查点。接口改变、文件范围扩大、一个包阻塞或审查发现跨包问题时，暂停受影响后续波次，重算并发；必要时串行或交回原 agent 返工。不因 `corral status=idle` 或回复 `DONE` 就认定顶层完成。主控检查全部必要验收、组合结果、审查结论、合并与项目收尾后统一结束。

派发前可给用户一段简短可核对的输出：**结论**（单路/分阶段/立即并行）；**理由与最大风险**；**波次**（包、依赖、文件与接口）；**人数**（开发总数/各波次/审查/工作峰值）；**集成与完成条件**。含糊任务可先调查再更新这段计划，不为表现“智能”而编造确定性。

## 剩余验证与待用户决定

1. **先采用哪一层：**仅本项目 `AGENTS.md` 小范围试行，还是希望所有使用 corral-dispatch 的项目都有此行为？前者是本报告建议，后者需要另开 corral 仓库任务并明确授权；T16 不修改两者。
2. **是否进行真实试行：**本轮只有同一主控的静态规划演练与合成排程，没有真实多 agent 的耗时、冲突率、返工率或新主控在盲题上的稳定判断率。下一阶段可先固定若干未知答案的顶层任务盲题，记录误拆/漏拆/人数偏差；合格后再选一件真实、可回滚任务试行。试行本身须另行决定和排期。
3. **进度可见性：**先接受顶层任务文件 + corral board + 现有 drover 看板，还是另立子任务看板需求？后者涉及数据来源和已定边界，不因本次规划研究自动启动。

本报告只作为 T16 的研究交付。未改 corral、corral-dispatch、业务代码、ROADMAP、loop/TASK_GATE、后台服务或真实队列状态；没有启动 agent、推送或做真实任务推进。
