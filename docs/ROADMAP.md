## R1 用 corral 完全替代 herdr

### 名字

**corral**（畜栏）。herdsman 是牧人，agent 是他放的牲口，corral 是圈牲口的围栏：每个 agent 关在自己的**栏位**里，
牧人知道哪个栏里是谁，随时能过去看一眼、吆喝一声。命令叫 `corral`，本机无同名命令。

### 目标

自己写 corral，**完全替代 herdr**：herdsman 的写手、规划者、评审方都跑在 corral 里。终点是**删掉 herdsman 里的 herdr 路径**，不再依赖任何现成的终端工具（herdr、tmux 都不用）。
corral 只用 Python 标准库，不引入新依赖。**交互方式保持不变**：agent 仍是交互式的，你随时能看、能点对话框、能插话。

思路：AI 时代的三样东西里，agent（Claude Code、Codex）是租来的；harness（herdsman 的协议、轮次、证据门槛、队列、看板）是自己的、值得精雕；
终端这层也拿回自己手里，但**只求够用**：送得进、看得见、挂不了。herdr 的多窗格布局、主题、会话恢复一样都不追。

### 隔离：corral 和 herdsman 是两个项目

corral 是**基础设施**，给 harness 提供支持，但不属于 herdsman。两者的关系和今天 herdr 与 herdsman 一样：herdr 不知道评审是什么，herdsman 只通过 herdr 的命令用它。corral 占的正是 herdr 这个位置，只不过是自己写的。

**两条判断标准**
1. **corral 不认识 herdsman**：corral 可以原样拿去给别的 harness 用；它的代码、文档、测试里没有「评审」「写手」「规划者」「项目」「队列」这类词。
2. **herdsman 只认 corral 的契约**：只通过 corral 公开的命令、输出格式和退出码使用它，**不读 corral 的任何内部文件**（栏位元数据、事件文件、socket）。

**两边之间只有一个契约**：corral 的命令、JSON 输出、退出码。契约写成 corral 自己的文档，带版本号。
以后 corral 怎么重写都不影响 herdsman；herdsman 怎么改流程也不影响 corral。

**各自独立的东西**

| | corral | herdsman |
|---|---|---|
| 仓库 | 独立仓库 | 现有仓库 |
| 安装 | corral 自己的安装脚本 | `install.sh` 只检查 corral 装了没有（和今天检查 herdr 一样），不安装、不管理它 |
| 升级 | 自己决定怎么处理正在跑的栏位 | 不知道栏位存在 |
| 测试 | 测自己，不依赖 herdsman | 用假的 `corral` 命令模拟（和今天模拟 herdr 一样），不依赖真的 corral |
| 版本 | 自己的版本号 | 声明需要的 corral 契约版本 |

**判断越界的信号**：herdsman 改需求（新的流程档位、新的队列命令、新的评审规则）时要改 corral；或者 herdsman 的代码里出现 corral 内部文件的路径。任一出现，说明边界划错了，先修边界。

### 为什么

- **单点依赖**：`install.sh` 把 herdr 当必需依赖检查；herdr 不在，`request-review` 一开头就 exit 2。
- **已经踩过它的坑**，都要靠脚本兜底：`agent prompt` 在 agent 进程还没起来时静默吞掉 prompt 却返回成功（09-06 复现）；`stalled` 误报；它靠识别屏幕内容判断状态，不稳。
- **协议本来就是文件**：request.md、findings.md（带 REVIEW-COMPLETE 结束标记）、responses、decision 全是文件。herdr 实际承担的只是「把 agent 拉起来、把话送进去、看它在不在干活」。

### 否掉的方案

- **无头模式**（`claude -p` / `codex exec`）：跑完就退出，看不到实时过程，审批和提问对话框没人接，不能中途插话。你一直盯着评审方看，这条路不适合。
- **tmux**：能交互，但它也是现成的外部工具，不符合「不依赖现有的东西」。
- **常驻内核服务**：讨论过「会话看守 + 可重启内核」两层，后来发现打开、塞消息、查找都不需要常驻进程，内核整层删掉，少一个会挂的东西。
- **重做一个 herdr**：herdr 是两套东西：常驻后台服务（工作区、标签、窗格、按屏幕识别 agent、通知、远程、worktree、更新）加终端里的前端（在一个窗口里画多个窗格，本质上是终端模拟器）。
  corral 两套都不重做：**没有前端**，画面交给 Ghostty；后台只留「持有伪终端、送文字、报状态」这一小块，而且拆成每个 agent 一个栏位，没有中心服务。

### 同类工具调研（2026-09-15）

有人在做类似的东西，但没有一个同时满足：保留 agent 自己的交互界面、没有中心进程、状态靠钩子而不是读屏、只做基础设施不带流程、不引入依赖。
带 agent 感知的工具大多是「一整套自己的东西」。

| 类别 | 工具 | 做法 | 和 corral 的关系 |
|---|---|---|---|
| 终端层「每会话一个进程」 | dtach、abduco | 每个会话一个服务进程，在自己的伪终端里启动命令；会话按名字对应一个本机 socket（abduco 放在 `~/.abduco`） | 就是「栏位」的模型，久经验证；但完全不认识 agent，没有状态和送达确认 |
| agent 托管 | herdr | 中心服务 + 终端前端，带命令行和 socket 接口；进程名匹配 + 读屏启发式判断状态 | 和工作区界面绑在一起，是中心进程 |
| agent 托管 | subagent-cli | 一个常驻守护进程管所有会话，node-pty + 无头终端模拟，读屏状态机，网页终端接入 | 中心进程；项目很早期 |
| agent 托管 | agent-yes（命令 `cy`） | **每个 agent 一个独立进程，没有中心守护进程**，靠共享文件登记；有 ls / tail / read / send / attach / stop；按正则匹配「就绪」画面 | 结构上最像 corral；但默认自动替 agent 回答「Yes」（违反 herdsman「不让 agent 代答审批」），带任务列表、问答等流程功能，依赖 Node 或 Bun |
| 协议标准 | ACP（Agent Client Protocol） | Zed、JetBrains 推的 JSON-RPC 标准，Claude Code、Codex 有适配器，编辑器通过它驱动 agent | 用编辑器界面替代 agent 自己的终端界面，不合要求 |

**为什么没有正好合适的**：状态判断最难通用。多数工具选读屏（零配置，但 agent 界面一改版就可能失灵）；钩子更可靠，但要给每家 agent 配置、还会碰到信任确认，多数工具不愿承担。另外多数工具在卖体验（界面、工作区、自动应答），所以都做成一整套。

**结论**：结构是对的（abduco 证明「每会话一个进程」长期稳定；agent-yes 独立选了「每个 agent 一个进程 + 文件登记」）。corral 的差异点是：钩子判断状态、送达确认、零依赖、严格不带流程。
试验前参考 abduco 的源码（伪终端、socket、脱离终端的细节）和 agent-yes 的文件登记设计，**只参考，不采用**。

来源：[abduco 手册](https://man.archlinux.org/man/abduco.1.en)、[abduco](https://github.com/martanne/abduco)、[subagent-cli](https://github.com/yejianfei/subagent-cli)、[agent-yes](https://github.com/snomiao/agent-yes)、[Herdr 文档](https://herdr.dev/docs/)、[ACP agents](https://agentclientprotocol.com/get-started/agents)

### 现状：herdsman 里 herdr 用在哪

| 位置 | 用途 | 调用 |
|---|---|---|
| `request-review` 传输层（已集中在一段里） | 按 cwd 找评审方 / 规划者 | `agent list`、`pane get`、`agent get` |
| 同上 | 没有就开 pane 并拉起 agent | `pane split`、`pane process-info`、`agent start` |
| 同上 | 送 prompt，并以状态变成 working / blocked 为送达证据 | `agent prompt --wait --until` |
| 同上 | 等待期间查评审方状态，发现卡住或没交付就停 | `agent get` → `agent_status` |
| `request-review` 唤醒（jb-finetune 开着 REVIEW_WAKE） | 评审交付后核对写手窗格身份、等它空闲、注入「再次运行 request-review」 | `HERDR_PANE_ID`、`agent get`、`agent prompt` |
| `review-board` | 顶栏和面板的 agent 状态、正在做什么 | `agent list`、`agent get`、`agent read` |
| `review-board serve` | 健康检查、外层循环叫醒写手 | `agent list`、`agent get`、`agent prompt` |
| `review-task` | 循环停下时记下写手所在 pane（本身不调 herdr） | `HERDR_PANE_ID` |

评审结果本身不经过 herdr：findings 是文件，写手自己运行的 request-review 去读。依赖 herdr 的是**送话、查状态、叫醒写手**。
没有 herdr 时脚本会退回前台等待，结果照样能拿到，但写手一直占着回合，评审方卡住要等超时才发现。

### 第一部分：corral（独立项目）

#### 职责：只管机制，不管策略

| corral 提供（机制） | 调用方自己决定（策略；对 herdsman 来说就是 harness） |
|---|---|
| **打开**：用一个名字拉起一个 agent | 名字怎么起、什么时候打开谁 |
| **塞消息**：往某个 agent 送一段文字，并确认送到 | 该送什么话、送给谁 |
| **查找**：某个名字的 agent 在哪、还活着没有 | 找到之后做什么 |
| **状态**：working / idle / blocked / 不存在 | 看到空闲之后该做什么、什么时候叫醒谁 |
| **接入**：让人进去看、点对话框、插话 | 拉起之后要不要自动弹出窗口、弹在哪 |
| **等待**：等某个 agent 这一轮结束 | 等完之后做什么 |
| **取回复**：某个 agent 上一轮的最后一条回复（干净文字） | 回复怎么用 |
| **关闭**：让某个 agent 退出 | 什么时候关、关哪个 |

名字是调用方给的普通字符串（比如 `jbfine/reviewer`），corral 不解释它的含义。

**和 herdr 的能力对照**

| herdr 的能力 | corral |
|---|---|
| 前端：多窗格渲染、布局、标签、工作区 | 不做，交给 Ghostty；一个 agent 占一个 Ghostty 标签或分屏 |
| 终端模拟：解析并维护每个窗格的画面 | 不做；`corral attach` 只原样转发字节，画面由 Ghostty 画 |
| 常驻服务持有所有窗格 | 没有中心服务；每个 agent 一个栏位，只持有自己的伪终端 |
| 按屏幕内容识别 agent 和状态 | 不做，改用 agent 自己的钩子 |
| 送 prompt 并等待 | 保留：`corral send`，以「收到输入」钩子为送达证据 |
| 查 agent 列表和状态 | 保留：`corral ls`、`corral status` |
| 读屏（渲染后的干净文字） | 不做；「正在做什么」改从钩子事件得到（最近调用的工具、这一轮已跑多久） |
| 通知、worktree、远程、更新渠道、配置热加载 | 不做（通知、worktree 在 herdsman 里本来就有） |

**稳定靠什么**：不解析 agent 输出（不会被某版 agent 界面变化搞坏）；没有中心进程（一个栏位出事只影响一个 agent）；栏位写好不改；命令跑完即退、状态在文件里；只用 Python 标准库。

#### 结构：栏位 + 命令 + 内部文件

**栏位**（每个 agent 一个极小的进程，**唯一常驻的东西**）
- 持有这个 agent 的伪终端（Python `pty`），agent 是它的子进程；栏位脱离启动它的命令独立运行（新会话）。
- 只做字节级的事：转发接入者的输入输出、写入一段文字、调整终端尺寸、保留最近输出。不解析内容。
- 顺带记两样终端层面的通用信息：**最后一次输出的时间**，以及 agent 设置的**终端标题**（终端标题是标准的终端功能，不是某家 agent 的界面内容）。
- 同一个 agent 的写入由栏位串行处理，两段文字不会交错。
- agent 退出，栏位记下退出码、删掉自己的 socket 后退出。
- **写好之后基本不改**。corral 升级时新版本只对之后打开的 agent 生效，正在跑的栏位不替换、不杀。

**`corral` 命令**（跑完就退出，不常驻；这就是对外契约）
- `corral start <名字> --cwd <目录> -- <agent 命令…>`：拿文件锁防止同名 agent 被拉起两次，启动栏位，输出实例编号。
  加 `--unique` 时把名字当前缀，corral 自动补一个不重复的后缀（如 `jbfine/ask-3`），输出最终名字。
- `corral send <名字> <文字>`：连上栏位写入文字（多行用终端粘贴模式包起来再回车），确认 agent 收到输入才返回成功；没收到重发一次，再失败就以约定的退出码报错。
- `corral status <名字>`：working / idle / blocked / 不存在，外加实例编号、最后一次输出的时间、终端标题、最近一次调用的工具和这一轮开始的时间（来自钩子）。
- `corral where <名字>` / `corral ls`：定位、确认进程还活着；栏位已死的残留顺手清掉。
- `corral read <名字>`：最近若干行原始输出，去掉控制字符。没有终端模拟，agent 界面重绘时文字会很乱，只作排查用；看板不靠它。
- `corral attach <名字>`：直接连栏位，原样转发输入输出。接入时触发一次终端尺寸变化让 agent 自己重绘，不实现终端模拟；按约定键退出，agent 继续跑。
  接入时把名字写进窗口标题，人看一眼就知道每个分屏里是谁（需要让写手交给某个 agent 时，按名字说）。
- `corral wait <名字>`：等到这个 agent 这一轮结束（空闲或弹框卡住），带超时；输出结束时的状态。
- `corral reply <名字>`：上一轮的最后一条回复，干净文字，来自 agent 适配（Claude Code 的回合结束钩子带对话记录位置，Codex 的回合结束事件带最后一条回复；见第 1 步实测）。
- `corral stop <名字>`：让 agent 正常退出，栏位随之退出。
- `corral attach --wait <名字>`：名字还不存在时显示「等待某某出现」，一出现就自动接上；agent 退出后回到等待，下次出现再接上。「等某个名字出现」是通用能力，不涉及任何流程。

所有查询命令都有 JSON 输出，退出码写进契约文档。

**内部文件**（corral 私有，格式随时可改，调用方不许读）
- 栏位元数据：名字、实例编号、cwd、agent 种类、pid、socket 路径、启动时间。
- 事件文件：agent 钩子报来的「会话开始」「收到输入」「调用工具前」「弹出权限请求」「回合结束」。`corral status` 和 `corral send` 的送达确认都从这里算出来。

布局示意（corral 内部，随时可改）：

```
~/.corral/
  jbfine/
    writer/          ← 名字 jbfine/writer 就是这个路径
      meta.json      ← 实例编号、pid、目录、启动命令、启动时间
      sock           ← 栏位在这里监听；连得上 = 还活着
      events         ← 这个 agent 的钩子往这里追加
    planner/   …
    reviewer/  …
```

`corral start jbfine/writer -- codex` 的过程：建目录并拿文件锁（同名不能再启动一个）→ 在后台起栏位，由栏位启动 codex，并把名字和实例编号放进 codex 的环境变量 → 栏位写 meta.json、开始监听 sock。
之后任何命令找它，都是按名字算出路径、连 sock：连得上就是它，连不上说明栏位已死，清掉残留、报「不存在」。

**agent 自己怎么知道自己是谁**：栏位启动 agent 时放进环境变量的名字和实例编号，agent 里运行的脚本会继承（今天 herdr 给写手传窗格编号也是这个办法）。

**实例编号防什么**：同一个名字的 agent 退出后又被重新启动，名字相同、实例编号不同。调用方比对实例编号，就不会把发给旧 agent 的话塞给一个毫不知情的新对话。

#### 终端有两层，agent 不绑定任何窗口

- **伪终端**：操作系统提供的一对字符设备。agent 从一头读键盘输入、往这一头写画面；谁拿着另一头，谁就能替它打字、看它的画面。agent 真正「跑在里面」的是这个。
- **终端窗口**（Ghostty 等）：只是显示器，把字节画成像素、把按键变成字节。

herdr 也从来没拿过 Ghostty 的窗口句柄：它的窗格编号是它后台服务里某个伪终端的编号。corral 同理，句柄是名字，对应一个栏位。

```
herdr：   agent ⇄ 伪终端 ⇄ herdr 后台服务（窗格编号） ⇄ herdr 前端    ⇄ 窗口
corral：  agent ⇄ 伪终端 ⇄ 栏位（名字）              ⇄ corral attach ⇄ 窗口
```

右边那截（前端或 attach 加窗口）随时可以断开、换个窗口再接；**给 agent 塞消息是经过栏位往伪终端写字节，完全不经过任何窗口**。所以系统只记名字，不记窗口。

#### 退出不影响运行：为什么成立

- **普通终端里关窗口为什么会带走程序**：窗口程序自己拿着伪终端的另一头；关窗口时这一头被关掉，操作系统给里面的程序发「终端挂断」信号，程序默认退出。
- **tmux、herdr 的办法**：伪终端的另一头由一个不属于窗口的后台进程拿着；窗口里跑的只是客户端。关窗口只死客户端，agent 收不到挂断信号。像远程桌面：关掉窗口，那台电脑上的程序照样跑。
- **corral**：拿着另一头的是栏位。栏位启动时 fork 两次、开新会话，彻底脱离启动它的窗口和命令，挂到系统进程（macOS 上是 launchd）名下，所以窗口或启动它的程序清理自己名下的进程时碰不到它。
  herdsman 的 request-review 里叫醒写手的后台进程已经在用同一招（当初就是被 codex 退出时连带杀掉过）。

```
关窗口之前：  codex ⇄ 伪终端 ⇄ 栏位 ⇄ corral attach ⇄ 窗口
关窗口之后：  codex ⇄ 伪终端 ⇄ 栏位                     （断开的只有右边）
再次接入：    codex ⇄ 伪终端 ⇄ 栏位 ⇄ corral attach ⇄ 另一个窗口
```

| 发生了什么 | agent 还在跑吗 |
|---|---|
| 关掉显示它的窗口，甚至退出整个 Ghostty | 在 |
| attach 里按约定键退出 | 在 |
| 发起它的脚本或 `corral` 命令结束 | 在 |
| 重装 herdsman、升级 corral | 在（栏位不被替换） |
| agent 自己退出（比如输入 /exit） | 不在；栏位删掉 sock、记下退出码后退出 |
| 有人手动杀掉栏位进程 | 不在 |
| 电脑重启 | 不在（tmux、herdr 也一样） |

#### 为什么每个 agent 一个栏位，而不是一个服务管所有

| | 一个服务管所有（tmux、herdr） | 每个 agent 一个栏位（corral） |
|---|---|---|
| 服务出问题 | 所有 agent 一起没 | 只影响那一个 agent |
| 「谁是谁」这张表 | 在服务内存里 | 在磁盘上，一个 agent 一个目录 |
| 升级 | 全部重启，或做复杂的交接（herdr 专门有带交接的更新命令） | 新版本只用于之后启动的 agent |
| 代码复杂度 | 一个进程同时照看很多伪终端和客户端 | 一个栏位只照看一个伪终端 |
| 列出所有 agent | 问服务一次 | 扫一遍目录 |
| 进程数 | 一个 | 有几个 agent 就有几个栏位 |

代价很小，本机实测（Python 3.14，加载栏位要用的标准库模块后空闲）：

```
每个栏位约 16 MB 内存，空闲时阻塞等数据，不轮询
```

两个项目各三个角色共六个栏位，合计约 100 MB，和 Claude Code、Codex 本身比可以忽略。以后真嫌进程多可以换成单服务，契约不变，但那样回到单点故障，现在不建议。

#### 栏位之间不沟通，也不需要找对方

每个栏位只守住自己那个 agent 的伪终端，等别人来连。**跑来跑去的是一次次运行完就退出的 `corral` 命令，由 harness 脚本调用。**
比方：每个栏位是一户人家，门牌号就是路径，门上有投信口（sock）；邻居之间从不串门；要给谁传话就派一次 `corral send` 按门牌号去塞纸条；真正的工作内容放在公共文件里，纸条上只写「去看某某文件」。

以 herdsman 的一个评审周期为例：

```
写手 codex（栏位 W 里）
  │ 1. 在自己的 shell 里运行 request-review（脚本是 codex 的子进程）
  ▼
request-review
  │ 2. 写 request.md ──────────────────────────→ 【文件】
  │ 3. corral start jbfine/reviewer   → 建起栏位 R，里面启动 claude
  │ 4. corral send jbfine/reviewer "去读 request.md 做评审"
  │      └→ 按路径连 R 的 sock → R 把字打进 claude
  │ 5. 留一个后台叫醒进程，自己退出，写手回合结束
  ▼
评审方 claude（栏位 R 里）
  │ 6. 读 request.md，写 findings.md ──────────→ 【文件】
  ▼
叫醒进程
  │ 7. 看到 findings.md 写完（读文件）
  │ 8. corral send jbfine/writer "评审完了，再运行 request-review"
  │      └→ 按路径连 W 的 sock → W 把字打进 codex
  ▼
写手 codex
    9. 运行 request-review，读 findings.md
```

栏位 W 和栏位 R 从来没有互相连过。**找得到**靠三条：名字就是地址（harness 按约定知道名字）；同一个用户、同一台机器看到的是同一个 `~/.corral`；连得上就在，连不上就是不在，由调用方决定要不要重新启动。

这和今天 herdr 的方式一样：request-review 执行 `herdr agent prompt <窗格编号>`，由 herdr 服务把字打进窗格，窗格之间同样不说话。区别只是 herdr 把「编号对应哪个伪终端」放在服务内存里，corral 让门牌号本身就是文件路径。

#### agent 适配属于 corral

认识 Claude Code 和 Codex、给它们配钩子，是 corral 的基础设施能力（herdr 也内置了这类适配），和评审无关。
- Claude Code 和 Codex（本机 0.154）都有「会话开始」「收到输入」「调用工具前」「弹出权限请求」「回合结束」钩子事件。
- 栏位启动 agent 时带上身份变量，钩子据此写对应的事件文件。
- **不动全局配置**：钩子只随栏位启动的那个 agent 生效。Claude Code 可用启动参数单独指定配置；Codex 能否按启动参数或按项目配钩子要实测（见第 1 步）。
- 不认识的 agent 种类也能打开和接入，只是状态报「未知」。

#### 给 agent 用的使用说明

herdr 给 agent 准备了使用说明，agent 读了就会切窗格、送 prompt、等待、读回复。corral 也自带一份，**只讲 corral 的命令怎么用，不涉及评审**，放在 corral 自己的仓库里。
写手（或任何 agent）读了它，就能自己开别的 agent、送话、等回复。

#### 使用场景：临时委派（不走任何流程，会大量使用）

人直接对写手说「开一个 Claude Code，把上面的想法交给它看一下」。这不走 herdsman 的评审流程，完全靠 corral 的通用命令完成：

```
写手（在自己的 shell 里）
  1. corral start jbfine/ask --unique --cwd <仓库> -- claude   → 得到名字 jbfine/ask-3
  2. corral send  jbfine/ask-3 "请看一下这个想法：……"          → 确认送达
  3. corral wait  jbfine/ask-3                                  → 等它这一轮答完
  4. corral reply jbfine/ask-3                                  → 拿到干净的回复文字
  5. 写手把回复整理后告诉人；需要追问就回到第 2 步
  6. 用完：corral stop jbfine/ask-3（或留着以后接着问）
```

- **人怎么看它**：在写手旁边预先挂一个 `corral attach --wait jbfine/ask-3` 分屏；想每次都自动出现，就固定用同一个名字 `jbfine/ask`（不加 `--unique`），分屏挂 `attach --wait jbfine/ask`。
- **两种起名方式都支持**，由调用方选：固定名字（接着上次的对话问）；`--unique`（每次一个干净的新对话，可以同时开好几个）。
- **大量使用时的清理**：临时 agent 不会自己退出，用完 `corral stop`；`corral ls` 能看到还有哪些开着。
- **明确不支持**：「交给右侧那个」这类位置说法。corral 不管窗口布局，只认名字；只有一个别的 agent 在跑时，调用方可以用 `corral ls` 自己认出来。
- **前提**：被委派的 agent 必须是用 `corral start` 启动的。在 Ghostty 里直接敲 `claude` 启动的，corral 看不见，送不进去。

#### 身份：句柄和 agent 一起诞生

herdr 是先有窗格、后在里面启动 agent，只能事后猜哪个窗格跑着谁；窗格编号还会被复用，所以今天 herdsman 的脚本要按 cwd 找评审方、比对终端编号和会话编号，
同目录的写手和规划者只能靠名字区分（代码里专门防过「自己等自己、自己叫自己」）。

corral 反过来：agent 由栏位启动，「谁是谁」在打开那一刻就写定。

| | herdr | corral |
|---|---|---|
| 句柄 | 窗格编号 | 名字 + 实例编号 |
| 身份怎么来 | 事后识别窗格里跑的是什么 | `corral start` 时由调用方给定名字，corral 发实例编号 |
| 怎么找到 | 按目录或名字搜索 | 按名字直接定位 |
| 同一目录跑两个 agent | 靠名字区分，会认错 | 名字不同就是两个栏位，不可能混 |
| agent 被换掉 | 比对终端编号和会话编号来防 | 再打开就是新的实例编号，调用方比对即可 |
| 关掉显示它的窗口 | 窗格没了，agent 也没了 | 什么都不影响，窗口只是观看者 |

#### 设计约束

- **栏位不能挂**：除栏位外没有任何常驻进程。
- **只听本机**：所有 socket 权限 0600，放在用户自己的目录下。
- **不摆窗口布局**：agent 运行的终端是栏位里的伪终端，不是屏幕上的任何窗口。没人接入时用默认尺寸，有人接入就换成接入窗口的尺寸。
- **多个窗口接同一个 agent**：只允许一个窗口打字，其余只读；终端尺寸跟着能打字的那个走。

#### 评估：能否完全支持现在的 herdsman

2026-09-15 按 `request-review`、`review-board`、`review-task` 里全部 herdr 调用和它们读的字段逐条对照。
**结论：功能上能覆盖每一处，没有做不到的；但有五处要补设计或先实测，一处体验会变化（有缓解办法）。**

| herdsman 现在靠 herdr 做的事 | corral 怎么做 | 评估 |
|---|---|---|
| 找评审方和规划者，同一目录有两个就停 | 按名字定位，文件锁防重复打开 | 支持，更可靠 |
| 开窗格、等 shell 稳定、再启动 agent、透传模型参数 | `corral start` 直接启动 agent，不经过 shell | 支持；等 shell 就绪那段逻辑整段不需要 |
| 等 agent 准备好接收输入 | 等「会话开始」钩子 | **要补**：缺口 1 |
| 送 prompt 并确认送到 | `corral send` + 「收到输入」钩子 | 支持，比 herdr 更硬 |
| 判断干活、空闲 | 钩子 | **要补**：缺口 2 |
| 判断弹框卡住 | 「弹出权限请求」钩子 | **要实测**：缺口 3 |
| 第二轮找回同一个评审方，身份变了就停 | 名字 + 实例编号 | 支持 |
| 评审完叫醒写手：写手知道自己是谁、核对身份、空闲才注入 | 栏位启动 agent 时设身份变量，写手里跑的脚本继承；叫醒前比对实例编号 | 支持（今天 herdr 的窗格变量在 Codex 写手里能继承，同一机制可行） |
| 外层循环叫醒写手 | 同上 | 支持 |
| 看板显示状态和标题 | `corral status`（含终端标题） | 支持 |
| 看板显示「正在做什么」（今天读屏抓「Working (47m · esc to interrupt)」） | 钩子里最近调用的工具 + 这一轮已跑多久 | **要补**：缺口 4 |
| 看板健康检查 | `corral ls` | 支持 |
| 评审方自动出现在写手旁边 | 人预先开好分屏运行 `corral attach --wait` | **基本能找回，待实测**：代价 6 |

**缺口**

1. **启动时的信任对话框，钩子看不见。** 在新目录第一次启动 Claude Code 或 Codex 会先问「是否信任这个目录」，这时钩子还没加载。herdr 读屏能看出卡住；corral 只能等超时后报「启动卡住，去接入看一眼」。结果仍是停下等人，只是晚一点、说不准原因。
2. **人按 Esc 打断时，状态会卡在「干活」。** Claude Code 的「回合结束」钩子在用户打断时不触发，Codex 是否一样要实测。后果是叫醒写手、外层循环一直等它空闲。
   解法：栏位报「最后一次输出的时间」（字节层面的通用信息，不解析内容），由调用方判断「很久没输出就当空闲」。
3. **弹框的覆盖面要实测。** 审批框有钩子，但「向用户提问」这类对话框是否都有对应事件，两家都要逐个确认。漏掉的会被当成「在干活」。
4. **「正在做什么」换了信息来源。** 从读屏改为钩子，信息量不少，显示形式会变。
5. **Codex 钩子有信任机制。** 本机 Codex 配置里有钩子信任记录，还有一个跳过信任的危险参数（`--dangerously-bypass-hook-trust`）。corral 给 Codex 配的钩子第一次可能弹信任确认；提前登记信任还是用那个参数，要实测。

**代价**

6. **评审方不会自己弹出来。** 今天 herdr 在写手右边自动切出窗格显示评审方，人什么都不用做就能盯着看；corral 不摆布局，默认看不到。
   **主要缓解**：在写手旁边预先开一个分屏，只运行一次 `corral attach --wait jbfine/reviewer`。评审方没启动时分屏显示等待；写手一发起评审、评审方被拉起，分屏里自动出现画面；评审方跨周期一直活着，分屏就一直连着。规划者同样可以留一个分屏。这样不需要 Ghostty 支持用命令开分屏。
   **次要缓解**：`.review.conf` 里的「自动打开命令」，但 Ghostty 能否从命令行在现有窗口里开分屏不确定，很可能只能开新窗口。
   你习惯盯着评审方看，这一条仍然影响最大，要实测 `--wait` 用起来是否顺手。

**持平**

- 人正在接入窗口里打字时恰好发生叫醒注入，文字会混在一起。herdr 现在也有同样的问题。

### 第二部分：herdsman 这边怎么接

- **传输层换实现**：`request-review` 保留今天那段传输层，里面的 herdr 调用换成 `corral` 命令。`review-board`（状态、健康检查、外层循环叫醒）、`review-task` 同理。协议文件一个不改。
- **起名**：herdsman 按「项目/角色」给 agent 起名，比如 `jbfine/writer`、`jbfine/planner`、`jbfine/reviewer`。这是 herdsman 的约定，corral 不知道。
- **叫醒写手防认错**：发起评审时记下写手的实例编号（从 `corral status` 拿），叫醒前再查一次，对不上不注入。取代今天比对终端编号和会话编号的做法。
- **写手身份**：`review-task` 从 `HERDR_PANE_ID` 换成通过 `corral` 命令查到的写手实例。
- **空闲判断**：状态是「干活」但很久没有输出，当作可能被人打断（缺口 2）；阈值是 herdsman 的策略，写在 `.review.conf`。
- **启动卡住**：打开后超时没收到「会话开始」，报「启动卡住，可能停在信任对话框，去接入看一眼」（缺口 1），和今天一样停下等人。
- **看板「正在做什么」**：显示 `corral status` 里的最近工具和本轮已跑时间（缺口 4）。
- **受管约定**：写手一律用 `corral start jbfine/writer …` 启动。绕开 corral 直接敲 `codex` 启动的写手不受管，和今天在 herdr 外面跑一样，脚本退回前台等待。

**临时委派的 agent 不影响流程**
- herdsman 只认 `writer`、`planner`、`reviewer` 三个角色名；其他名字（如 `jbfine/ask-3`）一概不管，看板也不把它们当成流程角色。
- 临时 agent 不要开在评审目录里：评审开始时脚本会把那个目录重置到指定提交。

**多个项目同时跑**
- 名字带项目前缀（`jbfine/writer`、`inksample/writer`），在 corral 里是不同目录，不会撞；每个项目的脚本从自己的 `.review.conf` 知道短名，只给自己的名字送话。
- 看板按项目分面板，每块用 `corral status <短名>/<角色>` 取状态，一一对应。
- **看板会比今天更准**：今天看板认角色靠猜（工作目录等于仓库的算写手、名字以 `pl-` 开头的算规划者、工作目录等于评审目录的算评审方），在仓库目录里随手开个别的 agent 可能被当成写手；以后只有叫 `jbfine/writer` 的才是写手。
- **前提：项目短名不重复**。短名就是 `herdsman-init <短名>` 给的那个，今天已经决定了交接目录 `~/.review/<短名>` 和评审目录 `~/wt/<短名>-review`，corral 的名字沿用它。
- **今天就存在的隐患（与 corral 无关）**：`herdsman-init` 不检查短名是否已被别的仓库用了；两个仓库用同一个短名，第二次会「已存在，跳过」，两个项目共用同一个交接目录。接第二个真实项目前，先给 `herdsman-init` 加这个检查。

**显示：在哪看由人决定**
- **写手**：你在 Ghostty 里开个标签运行 `corral start jbfine/writer …`，启动完直接接入当前标签，写手就在你开它的地方。
- **评审方、规划者**：由 request-review 在后台打开，默认不出现在任何窗口里；想看就在任意标签或分屏里 `corral attach jbfine/reviewer`。
- **想让评审方「自动出现在旁边」**：在写手旁边开一个分屏，运行一次 `corral attach --wait jbfine/reviewer`，之后每次评审都自动接上（代价 6 的主要缓解）。
- **需要你的时候**：评审方弹框卡住，看板的「等你」和系统通知里直接给出接入命令。
- **可选的自动弹出**：`.review.conf` 里一行「打开 agent 后执行的命令」，由你自己填（比如让 Ghostty 开个新标签运行 `corral attach`）。这是 herdsman 的策略，corral 不知道它的存在；不填就什么都不弹。
- 看几个 agent 就在自己终端里开几个标签或分屏各接一个。关掉任何一个窗口都不影响对应的 agent。

### 分步

1. **corral 试验（先做，决定做不做；在 corral 自己的仓库里）**：写最小的栏位和 `corral` 命令，只拉起一个一次性的 Claude Code 和一个 Codex，逐条验证：
   - 接入后画面能正常重绘，能正常打字、点对话框；
   - 多行文字能完整送进输入框并提交，`corral send` 能确认送达；
   - `corral status` 能稳定报出 working / idle / blocked，且不改全局配置；
   - 关掉接入窗口再接回来，agent 还活着；
   - 除栏位外没有常驻进程，`corral` 命令全部跑完即退；
   - **启动卡在信任对话框**时，`corral status` 能在限定时间内报出「启动未完成」，而不是一直「未知」（缺口 1）；
   - **人按 Esc 打断**后，两家 agent 的状态分别是什么；「最后一次输出时间」能否可靠地让调用方判断出空闲（缺口 2）；
   - **Codex 钩子信任**：corral 配的钩子在不改全局配置的前提下能否直接生效，还是必须用跳过信任的参数（缺口 5）；
   - **`corral attach --wait`** 在预先开好的分屏里：评审方被拉起时自动接上、评审方退出后回到等待、再次拉起又接上；另外顺带确认 Ghostty 能否用命令在现有窗口里开分屏（代价 6）。

   - **临时委派来回一趟**：写手（Codex）开一个 Claude Code、送话、`corral wait` 等完、`corral reply` 拿回干净回复；反过来 Claude Code 委派给 Codex 也走一遍。回复里多段文字、代码块都要完整。

   前五条是 corral 本身能不能成立；第六到九条决定 herdsman 接上去之后好不好用；第十条是人大量使用的临时委派。十条都有结论才往下走。
   前五条或第十条任何一条过不了，R1 结束；第六到九条过不了，按「止损点」里的规则处理。
2. **corral 正式版**：栏位、`corral` 命令、契约文档、corral 自己的安装脚本和测试（不依赖真 agent）。测试专门覆盖：同名并发打开只成功一个、栏位死后残留被识别、送达确认超时、升级 corral 不影响正在跑的栏位。
3. **herdsman：评审方、规划者改走 corral**：传输层加 corral 实现，`.review.conf` 里一个开关，默认仍是 herdr；herdsman 测试用假的 `corral` 命令。在 jb-finetune 上打开开关跑真实周期。
4. **herdsman：写手改走 corral**：叫醒写手、外层循环、`review-task` 的写手身份一起切换。从这一步起整个流程不再需要 herdr。
5. **herdsman：删掉 herdr 路径**：第 3、4 步都达到成功标准后，删除传输层里的 herdr 实现和开关，`install.sh` 改为检查 corral，手册第 11 部分「herdr 事实核对」移入历史。

### 怎么算成功

- 一台没有 herdr、没有 tmux 的机器，装好 corral 和 herdsman，按 QUICKSTART 能跑完一个两轮的代码评审周期，评审完写手被自动叫醒。
- 在 jb-finetune 连续跑 **10 个真实周期**：零次「送了没到」；评审方卡住（弹框、没交付就停）能在看板上看出来。
- 真实使用中重装过 herdsman、升级过 corral，正在跑的 agent 都不受影响。
- 隔离成立：corral 仓库里搜不到 herdsman 的概念；herdsman 代码里搜不到 corral 内部文件的路径。
- 你不需要为了看 agent 在干什么而回去开 herdr。
- 临时委派在日常大量使用中顺手：开、送、等、取回复一次成功，不需要为此回去开 herdr。
- 评审质量不下降：用 R2 第一步的度量对比切换前后。

### 止损点

- 第 1 步试验前五条任何一条过不了：R1 结束，herdr 保留。
- 第 1 步试验里 `attach --wait` 用起来不顺手，且 Ghostty 也开不了分屏：由你判断「评审方自动出现在旁边」是不是刚需。是刚需，R1 结束；不是，记下这个代价继续。
- 第 1 步试验里缺口 2、缺口 5 找不到可靠解法：R1 结束（状态不可靠会让叫醒写手和外层循环失灵）。
- 第 1 步试验里 `corral reply` 拿不到干净完整的回复：R1 结束（临时委派是大量使用的场景，靠读乱码不可接受）。
- 第 3 步开关打开后 **两周或 10 个周期**，出现以下任一条就把开关拨回 herdr：
  - 一次无法事后发现的「评审没跑却以为跑了」；
  - 栏位挂掉带走正在工作的 agent；
  - 为了 herdsman 的需求不得不改 corral，或 herdsman 不得不读 corral 的内部文件（边界划错了，先修边界再继续）；
  - 你觉得在终端里接来接去比 herdr 明显难用。

### 不做

- corral 不理解评审、不转发内容、不管队列和轮次、不摆窗口布局、不认识 herdsman。
- 不支持「右侧那个」「左边的」这类位置说法，只认名字。
- 不管理不是用 `corral start` 启动的 agent。
- herdsman 不读 corral 的内部文件，不安装、不升级、不管理 corral。
- 不重做 herdr：不做前端，不做常驻内核服务。
- 不做终端模拟、读屏、多窗格布局、主题、会话恢复。
- 不做网页里的终端（那需要现成的终端库，或者自己写一个终端模拟器）。
- 不做 Windows、远程机器支持。
- 不改 herdsman 的协议文件和评审规则。

## R2 引入 RSI

### 先对齐：这里的 RSI 指什么

**按「递归自我改进」（Recursive Self-Improvement）理解**：流程用自己产生的记录，发现自己的弱点，提出对自己规则的修改；修改本身也走同一套对抗评审和人的批准，生效后再被度量。一圈接一圈，所以叫递归。

改进的对象分两层，**先做第一层**：

1. **项目里的评审规则**：rubric、项目简报、风险图（`.review-map`）、AGENTS.md 里的评审段落、评审方和规划者的提示词。
2. **herdsman 自己的代码**：脚本、路由、看板。等第一层跑通、证明提案质量靠得住再说。

> 待确认：如果你说的 RSI 不是这个意思，或者想直接从第二层开始，改这一节再动手。

### 为什么

流程的自我评估机制实际上已经停转了，这正是手册第 12 部分预言的失效方式。jb-finetune 截至 2026-09-15：

| 记录 | 现状 |
|---|---|
| 归档的评审周期 | 143 个 |
| `precision.md` 里「误报 ?」没人填的行 | 267 行（填过的只有 1 行） |
| `escapes.md` 漏检记录 | 0 条，只有表头 |

也就是说，143 个周期里评审方有多少误报、漏了什么，**没有任何数据**。「报告连续干净」和「它什么都没抓到」从内部看一模一样。靠人手填表已经证明行不通。

已经有一个很小的雏形：风险图会根据未送审记录提出升级建议，看板上显示「风险图有 N 条建议，等你点头」。RSI 就是把这个模式推广到整套规则上。

### 闭环

```
记录（归档、裁决、timing、未送审、git 历史）
  → 评估（自动算误报、找漏检候选）
  → 复盘（每 N 个周期，由独立 agent 读记录，写修改提案）
  → 送审（提案作为 kind: plan 走对抗评审）
  → 人批准（看板上点头，和风险图建议一样）
  → 生效（提交规则文件）
  → 度量（下一批周期的误报 / 漏检 / 耗时，和生效前比）
  → 回到开头
```

### 分步

1. **自动评估**（先做，R1 也要用）
   - **误报**：从已有记录推出来，不再让人填。写手带证据拒绝、人裁决改判的，算误报；人维持原判的，不算。
   - **漏检候选**：扫 git 历史，找「后来的修复提交改的正是某次已评审提交碰过的行」，列为候选，写进 `escapes.md` 并标「待确认」。这是风险路由方案里一直没做的第 4 步。
   - 看板显示误报率和漏检候选数，按周期滑动。
2. **复盘提案**：每 10 个周期（或手动触发），让一个**不是当前评审方的模型**读这批周期的归档和第 1 步的度量，只输出提案文件：改哪个规则文件、改成什么、依据是哪几个周期、预期改善哪个指标。复盘者不直接改任何东西。
3. **提案送审和批准**：提案作为 kind: plan 走现有评审；评审通过后在看板上等人点头；点头才提交。
4. **前后对比**：每条生效的提案记下生效时的周期号，下一批 10 个周期后自动对比指标。变差的提案在看板上标出来，人决定是否回滚。
5. **第二层（herdsman 自身）**：第 1 到 4 步稳定运行、至少有 3 条提案被证明有效之后，才讨论要不要让复盘也提 herdsman 的代码修改。

### 护栏（不可被 RSI 修改的东西）

这些是手册第 12 部分认定的真正价值，复盘提案**不得触碰**，碰到的提案直接作废：

- evidence 门槛：每条 blocking 必须带 `file:line` 或复现命令。
- 稳定编号和范围冻结。
- 轮次上限、人裁决、止损点本身。
- 度量的定义。不允许「改规则」和「改怎么算好」出现在同一条提案里，防止自我刷分。

另外：

- 任何提案都要人点头才生效，没有自动合并。
- 复盘者和评审方用不同模型，避免自己给自己打分。
- 复盘有成本上限：一次复盘只读最近一批周期，不读全量归档。

### 怎么算成功

- 第 1 步上线后，`precision.md` 和 `escapes.md` 不再需要人手填，数字每个周期自动更新。
- 前 3 条生效的提案里，**至少 1 条**在对比期内让误报率或漏检数变好，且没有让评审耗时明显变长。

### 止损点

第 2 步开始后 **一个月或 3 次复盘**：

- 提案大多是空话或重复（你点头率低于三分之一），就停在第 1 步：保留自动度量，不做复盘提案。
- 发现提案绕过护栏（哪怕被拦下），先修护栏，再决定是否继续。

### 不做

- 不让任何 agent 在无人批准的情况下修改规则或代码。
- 不做在线学习、微调模型。
- 不追求全自动：人始终是批准者。

---

## 顺序

两件事互不阻塞，但建议：

1. **先做 R2 第 1 步（自动评估）**。它小、低风险，而且 R1 第 3 步需要它来回答「换成 corral，评审质量有没有变差」。
2. 然后 **R1 第 1 步（corral 试验）**。它不碰现有脚本，只回答「corral 能不能替代 herdr」。
3. 之后两条线按各自的分步推进，谁先碰到止损点谁先停。
