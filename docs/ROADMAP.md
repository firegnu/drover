## R1 drover：外循环独立成新项目，接到 corral / corral-dispatch 上

### 为什么整条重写（2026-09-20）

2026-09-15 那版 R1 的前提已经不成立：

- **corral 做完了**，不再是「要不要做的第二种底层」，而是既成的基础设施。
- **corral-dispatch 出现了**（corral 仓库里的编排技能，owlet 在用）：主控拆任务、写任务文件、派给别的 agent、审查、合并、收尾。这套正好覆盖了 herdsman 原来用「写手 + 评审方」双 agent 做的事。
- 因此问题从「corral 能不能替掉 herdr」变成了：**herdsman 去掉评审协议之后还剩什么，该放在哪一层**。

旧版 R1 里仍然有效的部分，已经并进下面：herdr 耦合面的逐条评估（集中在 `request-review` 的六个 `transport_*` 函数）、五个缺口、一个代价。其中**缺口 2（Esc 打断后状态卡住）和缺口 4（「正在做什么」）已被 corral 的 `status` 字段解决**（`last_output` / `idle_for`、`last_tool` / `turn_started`）；缺口 1（启动时的信任对话框钩子看不见）仍然存在，处理办法不变：超时后报「可能停在信任框，去 attach 看一眼」。

### 三层定位

| 层 | 是什么 | 认识什么 | 时间尺度 |
|---|---|---|---|
| corral | 基础设施 | 只认识「开 agent、送话、看状态」。不认识任何流程 | 进程级 |
| corral-dispatch | **内循环** | corral 的命令；一件活怎么拆、交给谁、审不审 | 分钟到小时，主控在场 |
| **drover** | **外循环** | corral 的命令；队列、闸门、什么时候叫醒、怎么记账 | 天级，无人值守 |

内循环不是那份技能本身，是「主控会话 + 技能」。跑起来的是主控（例如 `owlet/main`）；drover 的操作对象是那个 agent，它甚至不需要知道主控读的是哪份技能。

### 硬规矩：只能往下依赖

```
drover ──只依赖──> corral-dispatch（很薄：只依赖「活干完会以合进 main 的分支落地」这一条约定）
   └──只依赖──> corral（send / status / ls）
corral-dispatch ──只依赖──> corral
corral ──> 谁都不依赖
```

drover 对 corral-dispatch 的依赖薄到：**内循环全靠人手工做的项目，drover 照样能跑**。

**四条禁止**

1. corral-dispatch 的技能、模板、项目 AGENTS.md 里不出现队列、循环、drover 这类概念。不能写「做完去领下一件」。
2. 主控不能要求「有队列才能工作」。人手动喂它和队列喂它，它感觉不出区别。
3. 任务文件格式不为 drover 加字段。
4. **drover 只读内循环本来就会留下的痕迹**（git、任务文件），不要求主控为它多写任何东西。

**验证办法**（随时可真跑）

| 拆到 | 还剩什么 | 必须仍然能用 |
|---|---|---|
| 三层齐 | 队列自己跑几天 | 无人值守 |
| 拆掉 drover | owlet 今天的样子 | 人手动喂里程碑 |
| 再拆掉 corral-dispatch | corral 技能开个 agent 问问题 | 日常委派 |
| 再拆掉 corral | 自己开终端敲 claude | — |

另外：corral-dispatch 里搜不到队列、循环这类词；drover 不读 corral 的内部文件。

**三个会破坏它的诱惑**

1. corral-dispatch 里写「做完去领下一件」——内依赖外。
2. 让主控写个 done 标记文件——内依赖外，主控在做一件只对外循环有意义的事。
3. drover 缺个信息就去 corral 加字段——infra 依赖上层。最隐蔽，因为看起来只是「给 corral 加个小功能」。真要加，那字段必须对任何 harness 都通用。

### drover 管什么、不管什么

| 管 | 不管（内循环的事） |
|---|---|
| 队列：任务从哪来、什么顺序、插队、暂停、放弃 | 怎么拆 |
| 推进：做完自动送下一件；停住了叫醒 | 交给哪家 |
| 闸门：什么时候必须停下等人 | 几档 |
| 观察：看板 | 审不审、怎么审 |
| 记账：耗时、返工轮数、路由的实际表现 | 合不合得了 |

`review-task` 今天的队列语义（add / next / done / go / pause / hold / move / edit / drop，放行模式 vs 自动模式）整套落在左栏，**一条都不改语义**，只换传输层。

### drover 的全部动作

**它一个 agent 都不开、不关、不接入。** 主控由人开、由人关，一直活着。

1. 往主控送一句话（任务正文）
2. 只读核对 git

用到的 corral 命令只有三个：`send`、`status`、`ls`。`start` / `stop` / `attach` 一个不用。

由此：

- **叫醒送的是任务正文本身**，和人手动粘一段任务进去一模一样。今天 `loop_tick` 送的固定那句 `LOOP_PROMPT`（让写手去跑 `review-task next`）**就是内依赖外，必须改掉**——这是这条规矩能不能立住的关键。
- 主控不在（`corral status` 查不到）：不重开，挂进看板「等你」，停止送任务。
- 主控上下文会涨，不用 drover 管：Claude Code 自己压缩；任务正文每次自带，任务文件和交接文件都在磁盘上。

### 完成判据：纯 git，零解析

drover 在送出任务**之前**记下 `main` 的 sha，之后反复查三条：

1. `main` 前进了（sha 变了）；
2. 没有残留的里程碑分支（`git branch --list '<前缀>-*'` 为空）；
3. 验收命令退出码为 0（队列条目里写，例如 `cd backend && uv run pytest -q`）。

三条都满足才算完成。队列条目可以覆盖默认判据——人在 queue.md 里写这件活算完的标准，本来就是人的活。

`review-task done` 今天那条「**只读核对 git 和交接目录，不听写手一句话**」原则原样保留，只换判据内容。

**不解析「## 主控审查」那一节。** 它是自然语言（「结论：通过，已合并进 main（sha）」），解析它等于把内循环的书写方式固化进 drover，主控换个措辞就崩——正是第 2 条诱惑。

**「它在等人」怎么识别**：主控 idle 了但判据没满足，它就停在某处等人拍板（审查复核两轮没过、和审查者有分歧、要推送、要花钱、发现设计对不上）。不需要内循环配合。

### 看板

骨架全留：深色配色（`color-scheme:dark` 那套 CSS 变量）、「不存自己的状态，刷新等于重跑」、静态页 + `serve` 双模式、HTTP 操作、系统通知、launchd 定时。换掉的是中间那块内容。

| 现在 | 之后 |
|---|---|
| 队列（含 go / pause / hold / move / edit / drop） | 原样留 |
| 「等你」横幅 + 系统通知 | 原样留 |
| 健康检查 | 留，数据源换成 `corral ls` |
| 写手 / 规划者 / 评审方三个状态块 | 改：主控一个块 + 当前派出去的 agent 若干块 |
| 周期、findings、轮次、severity、待裁决 | 删 |
| self-closed、简报状态、上次评审以来的提交、风险图建议 | 删（风险图看待定项） |
| 归档（最近 5 个周期） | 改：最近几件做完的任务，数据取自队列事件 |

新的页面结构（从上到下）：顶栏（项目、主控状态、健康红点）→「等你」横幅（每条带接入命令）→ **当前这件活**（主控状态 / 正在调什么工具 / 这一轮多久；派出去的 agent 各自状态；分支进展：几个提交、最后一次多久前；完成判据过了几条）→ 队列 → 做完的（耗时、派了几个 agent、返工几轮）→ 记账。

### 新仓库

**名字 drover**（赶牲口走长途的人）。和 herdsman 正好对照：herdsman 管一天的事，drover 管走几百里；它不决定去哪，只负责队伍一直在走。

**用 `git clone` 起步**，第一个提交就是「删掉评审那一套」：

- `review-board`、`review-task` 的完整历史全在，以后查某个判断为什么这么写，`git log` 照样查得到；
- 那个删除提交本身是主题变更的分界标记；
- 不用手工搬文件，不会漏。

**不用分支**：分支永远合不回来（main 是 herdr 版、jb-finetune 还在用），两条线的差异是「不同的项目」而不是「同一个项目的两个版本」；而且仓库名 `bounded-adversarial-review` 正是被砍掉的那部分，留在同一个仓库会一直误导。

**老仓库冻结，不删**：main 保持现状，jb-finetune 继续跑在 herdr 上，README 顶上加一行指向 drover 说明主题分家。等 drover 在 owlet 上跑稳、且决定 jb-finetune 也搬过来时，再定老仓库是归档还是删。

### 分步

1. **设计定稿**（本节）。
2. **建 drover 仓库**：clone + 一个删除提交；README 重写；老仓库 README 加指向。不建 GitHub 远端（等人明确说）。
3. **完成判据与配置**：定配置文件（叫什么、放哪、字段：主控名字、任务文件目录、分支前缀、默认完成判据、放行模式）；实现三条判据的只读核对。
4. **`review-task` 换传输层**：`HERDR_PANE_ID` → corral 名字 + 实例编号；叫醒改送任务正文。
5. **看板改造**：按上面的留 / 改 / 删；`loop_tick` 的 `herdr agent get/prompt` → `corral status/send`（`send` 自带退出码 7「不是 idle」和 8「30 秒内有人在打字」，今天手写的那些判断可以删）。
6. **在 owlet 上真跑**：先放行模式（每件做完等人 go），稳了再试自动模式。
7. **决定 jb-finetune**：搬过来、留在 herdr、还是停掉。

### 怎么算成功

- 一台没有 herdr、没有 tmux 的机器上，drover 能把队列里的任务一件接一件送进主控，人不在场时队列继续推进。
- 在 owlet 上连续跑 **10 件任务**：零次「送了没到」；零次「没做完却判成做完了」；主控停下等人时，看板和通知能在 5 分钟内让人知道。
- **拆掉 drover，owlet 照常工作**（真跑一遍验证依赖方向）。
- corral 一行没改；corral-dispatch 的技能文件里搜不到队列、循环这类词。
- 重装 drover、升级 corral，正在跑的 agent 都不受影响。

### 止损点

- **第 3 步**定不出「不解析自然语言」的完成判据：R1 结束，drover 不做，队列继续靠人手动喂。
- **第 6 步开始后两周或 10 件任务**，出现以下任一条就停掉自动送任务、退回手动：
  - 一次「没做完却判成做完了」，且事后查不出原因；
  - 为了 drover 的需求不得不改 corral 或 corral-dispatch（边界划错了，先修边界再继续）；
  - 主控被送进来的任务打断正在做的事（送达时机判断失效）；
  - 你觉得盯着看板比自己手动喂任务还累。

### 待定（不在本次定）

1. **目标项目**：先在 owlet 上跑；jb-finetune 什么时候搬、搬不搬。
2. **`review-map`（风险图）去留**：它和 corral-dispatch 的 `route.py` 都在判「这次改动要不要审、审多深」，但风险图是**有记忆的**（从归档证据里长出来：哪些路径出过 blocking、扇入多少、有没有测试），route.py 每次只拿三五句摘要问模型。三种选择：删掉、留着喂 route.py、单独留着当看板的一个提示。
3. **记账记什么**：`precision.md` / `escapes.md` 的评审口径没有了，换成耗时、返工轮数、路由判了什么/主控推翻没有。
4. **要不要读任务文件开头那行「路由：…」**：读它等于依赖内循环的一个书写格式（擦边，但不要求主控多做事）。倾向「读，但降级处理」——解析失败就不显示这一项，绝不参与任何判断。不读的话这个数据只能靠人手工翻任务文件统计。

### 不做

- drover 不开、不关、不接入任何 agent。
- 不做评审协议、不做 findings、不做轮次、不做证据门槛。
- 不自动重开主控，不自动关任何 agent。
- 不解析主控写的自然语言结论。
- 不读 corral 的内部文件，不安装、不升级、不管理 corral。
- 不为 drover 的需求改 corral 或 corral-dispatch。
- 不做 Windows、远程机器支持。

## R2 引入 RSI

### 先对齐：这里的 RSI 指什么

**按「递归自我改进」（Recursive Self-Improvement）理解**：流程用自己产生的记录，发现自己的弱点，提出对自己规则的修改；修改本身也走同一套对抗评审和人的批准，生效后再被度量。一圈接一圈，所以叫递归。

改进的对象分两层，**先做第一层**：

1. **项目里的评审规则**：rubric、项目简报、风险图（`.review-map`）、AGENTS.md 里的评审段落、评审方和规划者的提示词。
2. **herdsman 自己的代码**：脚本、路由、看板。等第一层跑通、证明提案质量靠得住再说。

> 待确认：如果你说的 RSI 不是这个意思，或者想直接从第二层开始，改这一节再动手。

### 为什么

流程的自我评估机制实际上已经停转了，这正是手册第 12 部分预言的失效方式。jb-finetune 截至 2026-09-15：

| 记录 | 现状 |
|---|---|
| 归档的评审周期 | 143 个 |
| `precision.md` 里「误报 ?」没人填的行 | 267 行（填过的只有 1 行） |
| `escapes.md` 漏检记录 | 0 条，只有表头 |

也就是说，143 个周期里评审方有多少误报、漏了什么，**没有任何数据**。「报告连续干净」和「它什么都没抓到」从内部看一模一样。靠人手填表已经证明行不通。

已经有一个很小的雏形：风险图会根据未送审记录提出升级建议，看板上显示「风险图有 N 条建议，等你点头」。RSI 就是把这个模式推广到整套规则上。

### 闭环

```
记录（归档、裁决、timing、未送审、git 历史）
  → 评估（自动算误报、找漏检候选）
  → 复盘（每 N 个周期，由独立 agent 读记录，写修改提案）
  → 送审（提案作为 kind: plan 走对抗评审）
  → 人批准（看板上点头，和风险图建议一样）
  → 生效（提交规则文件）
  → 度量（下一批周期的误报 / 漏检 / 耗时，和生效前比）
  → 回到开头
```

### 分步

1. **自动评估**（先做，R1 也要用）
   - **误报**：从已有记录推出来，不再让人填。写手带证据拒绝、人裁决改判的，算误报；人维持原判的，不算。
   - **漏检候选**：扫 git 历史，找「后来的修复提交改的正是某次已评审提交碰过的行」，列为候选，写进 `escapes.md` 并标「待确认」。这是风险路由方案里一直没做的第 4 步。
   - 看板显示误报率和漏检候选数，按周期滑动。
2. **复盘提案**：每 10 个周期（或手动触发），让一个**不是当前评审方的模型**读这批周期的归档和第 1 步的度量，只输出提案文件：改哪个规则文件、改成什么、依据是哪几个周期、预期改善哪个指标。复盘者不直接改任何东西。
3. **提案送审和批准**：提案作为 kind: plan 走现有评审；评审通过后在看板上等人点头；点头才提交。
4. **前后对比**：每条生效的提案记下生效时的周期号，下一批 10 个周期后自动对比指标。变差的提案在看板上标出来，人决定是否回滚。
5. **第二层（herdsman 自身）**：第 1 到 4 步稳定运行、至少有 3 条提案被证明有效之后，才讨论要不要让复盘也提 herdsman 的代码修改。

### 护栏（不可被 RSI 修改的东西）

这些是手册第 12 部分认定的真正价值，复盘提案**不得触碰**，碰到的提案直接作废：

- evidence 门槛：每条 blocking 必须带 `file:line` 或复现命令。
- 稳定编号和范围冻结。
- 轮次上限、人裁决、止损点本身。
- 度量的定义。不允许「改规则」和「改怎么算好」出现在同一条提案里，防止自我刷分。

另外：

- 任何提案都要人点头才生效，没有自动合并。
- 复盘者和评审方用不同模型，避免自己给自己打分。
- 复盘有成本上限：一次复盘只读最近一批周期，不读全量归档。

### 怎么算成功

- 第 1 步上线后，`precision.md` 和 `escapes.md` 不再需要人手填，数字每个周期自动更新。
- 前 3 条生效的提案里，**至少 1 条**在对比期内让误报率或漏检数变好，且没有让评审耗时明显变长。

### 止损点

第 2 步开始后 **一个月或 3 次复盘**：

- 提案大多是空话或重复（你点头率低于三分之一），就停在第 1 步：保留自动度量，不做复盘提案。
- 发现提案绕过护栏（哪怕被拦下），先修护栏，再决定是否继续。

### 不做

- 不让任何 agent 在无人批准的情况下修改规则或代码。
- 不做在线学习、微调模型。
- 不追求全自动：人始终是批准者。
