## R1 用 corral 完全替代 herdr

### 名字

**corral**（畜栏）。herdsman 是牧人，agent 是他放的牲口，corral 是圈牲口的围栏：每个 agent 关在自己的**栏位**里，
牧人知道哪个栏里是谁，随时能过去看一眼、吆喝一声。命令叫 `corral`，本机无同名命令。

### 目标

自己写 corral，**完全替代 herdr**：写手、规划者、评审方都关进 corral。终点是**删掉 herdr 那条路径**，herdsman 不再依赖任何现成的终端工具（herdr、tmux 都不用）。
只用 Python 标准库，不引入新依赖。**交互方式保持不变**：agent 仍是交互式的，你随时能看、能点对话框、能插话。

思路：AI 时代的三样东西里，agent（Claude Code、Codex）是租来的；harness（herdsman 的协议、轮次、证据门槛、队列、看板）是自己的、值得精雕；
终端这层也拿回自己手里，但**只求够用**：送得进、看得见、挂不了。herdr 的多窗格布局、主题、会话恢复一样都不追。

### 为什么

- **单点依赖**：`install.sh` 把 herdr 当必需依赖检查；herdr 不在，`request-review` 一开头就 exit 2。
- **已经踩过它的坑**，都要靠脚本兜底：`agent prompt` 在 agent 进程还没起来时静默吞掉 prompt 却返回成功（09-06 复现）；`stalled` 误报；它靠识别屏幕内容判断状态，不稳。
- **协议本来就是文件**：request.md、findings.md（带 REVIEW-COMPLETE 结束标记）、responses、decision 全是文件。herdr 实际承担的只是「把 agent 拉起来、把话送进去、看它在不在干活」。

### 否掉的方案

- **无头模式**（`claude -p` / `codex exec`）：跑完就退出，看不到实时过程，审批和提问对话框没人接，不能中途插话。你一直盯着评审方看，这条路不适合。
- **tmux**：能交互，但它也是现成的外部工具，不符合「不依赖现有的东西」。
- **常驻内核服务**：讨论过「会话看守 + 可重启内核」两层，后来发现打开、塞消息、查找都不需要常驻进程，内核整层删掉，少一个会挂的东西。

### 现状：herdr 用在哪

| 位置 | 用途 | 调用 |
|---|---|---|
| `request-review` 传输层（已集中在一段里） | 按 cwd 找评审方 / 规划者 | `agent list`、`pane get`、`agent get` |
| 同上 | 没有就开 pane 并拉起 agent | `pane split`、`pane process-info`、`agent start` |
| 同上 | 送 prompt，并以状态变成 working / blocked 为送达证据 | `agent prompt --wait --until` |
| 同上 | 等待期间查评审方状态，发现卡住或没交付就停 | `agent get` → `agent_status` |
| `request-review` 唤醒（jb-finetune 开着 REVIEW_WAKE） | 评审交付后核对写手窗格身份、等它空闲、注入「再次运行 request-review」 | `HERDR_PANE_ID`、`agent get`、`agent prompt` |
| `review-board` | 顶栏和面板的 agent 状态、正在做什么 | `agent list`、`agent get`、`agent read` |
| `review-board serve` | 健康检查、外层循环叫醒写手 | `agent list`、`agent get`、`agent prompt` |
| `review-task` | 循环停下时记下写手所在 pane（本身不调 herdr） | `HERDR_PANE_ID` |

评审结果本身不经过 herdr：findings 是文件，写手自己运行的 request-review 去读。依赖 herdr 的是**送话、查状态、叫醒写手**。
没有 herdr 时脚本会退回前台等待，结果照样能拿到，但写手一直占着回合，评审方卡住要等超时才发现。

### 边界：corral 只管机制，不管策略

herdsman 里 agent 之间从不直接说话，沟通的内容全在文件里，谁在什么时候做什么由 harness 脚本决定。
corral 不是传话的桥，只负责管住各个角色的 agent。

| corral 管（机制） | corral 不管（策略，留在 harness） |
|---|---|
| **打开**：按项目和角色拉起一个 agent | 评审轮次、证据门槛、队列、外层循环 |
| **塞消息**：往某个 agent 送一句话，并确认送到 | 该送什么话、送给谁 |
| **查找**：某个项目的某个角色在哪、还活着没有 | 看到空闲之后该做什么、什么时候叫醒写手 |
| **接入**：让人进去看、点对话框、插话 | 拉起之后要不要自动弹出窗口 |

agent 在干活还是空闲、有没有弹框，不经过 corral：agent 的钩子写进事件文件，谁要谁读。

**判断标准**：herdsman 改需求（新的流程档位、新的队列命令、新的评审规则）时，corral 一行都不用改。哪天发现要为了 herdsman 的需求改 corral，说明边界划错了，先修边界。

### 结构：栏位 + 命令 + 文件

**栏位**（每个 agent 一个极小的进程，**唯一常驻的东西**）
- 持有这个 agent 的伪终端（Python `pty`），agent 是它的子进程；栏位脱离启动它的命令独立运行（新会话）。
- 只做字节级的事：转发接入者的输入输出、写入一段文字、调整终端尺寸、保留最近输出。不解析内容，不知道 herdsman 的存在。
- 同一个 agent 的写入由栏位串行处理，两句话不会交错。
- agent 退出，栏位记下退出码、删掉自己的 socket 后退出。
- **写好之后基本不改**。新版本只对之后打开的 agent 生效，正在跑的栏位不替换。

**`corral` 命令**（跑完就退出，不常驻）
- `corral start jbfine 评审方 -- claude …`：拿文件锁防止同一角色被拉起两次，启动栏位，写下元数据。
- `corral send jbfine 写手 "……"`：连上栏位写入文字（多行用终端粘贴模式包起来再回车），然后等事件文件里出现「收到输入」作为送达证据；没收到重发一次，再失败就报错退出。
- `corral where jbfine 评审方` / `corral ls`：按固定路径直接定位，确认进程还活着；栏位已死的残留文件顺手清掉。
- `corral attach jbfine 评审方`：直接连栏位，原样转发输入输出。接入时触发一次终端尺寸变化让 agent 自己重绘，不实现终端模拟；按约定键退出，agent 继续跑。

**文件**
- 栏位元数据：项目、角色、实例编号、cwd、agent 种类、pid、socket 路径、启动时间。
- 事件文件：Claude Code 和 Codex（本机 0.154）的钩子在「收到输入」「回合结束」「弹出权限请求」「会话开始」时各追加一行。栏位启动 agent 时带上身份变量，钩子据此写对应的文件。
- 协议文件：request、findings、responses、decision，保持原样。

### 身份：句柄和 agent 一起诞生

herdr 是先有窗格、后在里面启动 agent，只能事后猜哪个窗格跑着谁；窗格编号还会被复用，所以今天的脚本要按 cwd 找评审方、比对终端编号和会话编号，
同目录的写手和规划者只能靠名字区分（代码里专门防过「自己等自己、自己叫自己」）。

corral 反过来：agent 由栏位启动，「谁是谁」在打开那一刻就写定。

| | herdr | corral |
|---|---|---|
| 句柄 | 窗格编号 | 栏位：一个 socket 加一份元数据 |
| 身份怎么来 | 事后识别窗格里跑的是什么 | `corral start` 时写下项目、角色、实例编号 |
| 怎么找到 | 按目录或名字搜索 | 「项目 + 角色」就是固定路径，直接定位 |
| 同目录的写手和规划者 | 靠名字区分，会认错 | 角色是路径的一部分，不可能混 |
| agent 被换掉 | 比对终端编号和会话编号来防 | 再打开就是新的实例编号；叫醒写手前比对实例编号，对不上不注入 |
| 关掉显示它的窗口 | 窗格没了，agent 也没了 | 什么都不影响，窗口只是观看者 |

约定：受管的 agent 一律用 `corral start` 启动。绕开 corral 直接敲 `codex` 启动的写手不受管，和今天在 herdr 外面跑一样，脚本退回前台等待。

### 显示：在哪看由人决定

- agent 运行的终端是栏位里的伪终端，不是屏幕上的任何窗口。没人接入时用默认尺寸，有人接入就换成接入窗口的尺寸。
- **写手**：你在 Ghostty 里开个标签运行 `corral start … 写手`，启动完直接接入当前标签，写手就在你开它的地方。
- **评审方、规划者**：由 request-review 在后台打开，默认不出现在任何窗口里；想看就在任意标签或分屏里 `corral attach`。
- **需要你的时候**：评审方弹框卡住，看板的「等你」和系统通知里直接给出接入命令。
- **多个窗口接同一个 agent**：只允许一个窗口打字，其余只读；终端尺寸跟着能打字的那个走。
- **可选的自动弹出**：`.review.conf` 里一行「打开 agent 后执行的命令」，由你自己填（比如让 Ghostty 开个新标签运行 `corral attach`）。这是策略，只在 harness 里，corral 不知道它的存在；不填就什么都不弹。

### 设计约束

- **栏位不能挂**：除栏位外没有任何常驻进程；`install.sh` 永远不杀栏位。
- **只听本机**：所有 socket 权限 0600，放在用户自己的目录下。
- **不动全局配置**：钩子只随栏位启动的那个 agent 生效。Claude Code 可用启动参数单独指定配置；Codex 能否按启动参数或按项目配钩子要实测（见第 1 步）。
- **不追 herdr 的界面**：看几个 agent 就在自己终端里开几个标签或分屏各接一个。这是和现在最大的体验差别。

### 分步

1. **试验（先做，决定做不做）**：写最小的栏位和 `corral` 命令，只拉起一个一次性的 Claude Code 和一个 Codex，逐条验证：
   - 接入后画面能正常重绘，能正常打字、点对话框；
   - 多行 prompt 能完整送进输入框并提交，且事件文件里出现「收到输入」；
   - 钩子能稳定写出 working / idle / blocked 对应的事件，且不改全局配置；
   - 关掉接入窗口再接回来，agent 还活着；
   - 除栏位外没有常驻进程，`corral` 命令全部跑完即退，状态全在文件里。

   五条都过才往下走；任何一条过不了，把卡在哪记进本节，R1 结束。
2. **正式版**：栏位和 `corral` 命令，带测试（沿用现有 mock 方式，不依赖真 agent）。测试专门覆盖：同一角色并发打开只成功一个、栏位死后残留文件被识别、送达证据超时。
3. **评审方、规划者改走 corral**：`.review.conf` 里一个开关，默认仍是 herdr；在 jb-finetune 上打开跑真实周期。
4. **写手改走 corral**：叫醒写手、外层循环、`review-task` 的写手身份（从 `HERDR_PANE_ID` 换成 corral 的实例编号）一起切换。从这一步起整个流程不再需要 herdr。
5. **删掉 herdr 路径**：第 3、4 步都达到成功标准后，删除传输层里的 herdr 代码和开关，`install.sh` 不再检查 herdr，手册第 11 部分「herdr 事实核对」移入历史。

脚本侧只改调用方：`request-review` 传输段、`review-board`（状态、健康检查、外层循环叫醒）、`review-task`。协议文件一个不改。

### 怎么算成功

- 一台没有 herdr、没有 tmux 的机器，按 QUICKSTART 能跑完一个两轮的代码评审周期，评审完写手被自动叫醒。
- 在 jb-finetune 连续跑 **10 个真实周期**：零次「送了没到」；评审方卡住（弹框、没交付就停）能在看板上看出来。
- 真实使用中重装过 herdsman（`install.sh`），正在跑的 agent 不受影响。
- 你不需要为了看 agent 在干什么而回去开 herdr。
- 评审质量不下降：用 R2 第一步的度量对比切换前后。

### 止损点

- 第 1 步试验五条里任何一条过不了：R1 结束，herdr 保留。
- 第 3 步开关打开后 **两周或 10 个周期**，出现以下任一条就把开关拨回 herdr：
  - 一次无法事后发现的「评审没跑却以为跑了」；
  - 栏位挂掉带走正在工作的 agent；
  - 为了 herdsman 的需求不得不改 corral（边界划错了，先修边界再继续）；
  - 你觉得在终端里接来接去比 herdr 明显难用。

### 不做

- corral 不理解评审、不转发内容、不管队列和轮次、不摆窗口布局。
- 不做常驻内核服务。
- 不做终端模拟、多窗格布局、主题、会话恢复。
- 不做网页里的终端（那需要现成的终端库，或者自己写一个终端模拟器）。
- 不做 Windows、远程机器支持。
- 不改协议文件和评审规则。

## R2 引入 RSI

### 先对齐：这里的 RSI 指什么

**按「递归自我改进」（Recursive Self-Improvement）理解**：流程用自己产生的记录，发现自己的弱点，提出对自己规则的修改；修改本身也走同一套对抗评审和人的批准，生效后再被度量。一圈接一圈，所以叫递归。

改进的对象分两层，**先做第一层**：

1. **项目里的评审规则**：rubric、项目简报、风险图（`.review-map`）、AGENTS.md 里的评审段落、评审方和规划者的提示词。
2. **herdsman 自己的代码**：脚本、路由、看板。等第一层跑通、证明提案质量靠得住再说。

> 待确认：如果你说的 RSI 不是这个意思，或者想直接从第二层开始，改这一节再动手。

### 为什么

流程的自我评估机制实际上已经停转了，这正是手册第 12 部分预言的失效方式。jb-finetune 截至 2026-09-15：

| 记录 | 现状 |
|---|---|
| 归档的评审周期 | 143 个 |
| `precision.md` 里「误报 ?」没人填的行 | 267 行（填过的只有 1 行） |
| `escapes.md` 漏检记录 | 0 条，只有表头 |

也就是说，143 个周期里评审方有多少误报、漏了什么，**没有任何数据**。「报告连续干净」和「它什么都没抓到」从内部看一模一样。靠人手填表已经证明行不通。

已经有一个很小的雏形：风险图会根据未送审记录提出升级建议，看板上显示「风险图有 N 条建议，等你点头」。RSI 就是把这个模式推广到整套规则上。

### 闭环

```
记录（归档、裁决、timing、未送审、git 历史）
  → 评估（自动算误报、找漏检候选）
  → 复盘（每 N 个周期，由独立 agent 读记录，写修改提案）
  → 送审（提案作为 kind: plan 走对抗评审）
  → 人批准（看板上点头，和风险图建议一样）
  → 生效（提交规则文件）
  → 度量（下一批周期的误报 / 漏检 / 耗时，和生效前比）
  → 回到开头
```

### 分步

1. **自动评估**（先做，R1 也要用）
   - **误报**：从已有记录推出来，不再让人填。写手带证据拒绝、人裁决改判的，算误报；人维持原判的，不算。
   - **漏检候选**：扫 git 历史，找「后来的修复提交改的正是某次已评审提交碰过的行」，列为候选，写进 `escapes.md` 并标「待确认」。这是风险路由方案里一直没做的第 4 步。
   - 看板显示误报率和漏检候选数，按周期滑动。
2. **复盘提案**：每 10 个周期（或手动触发），让一个**不是当前评审方的模型**读这批周期的归档和第 1 步的度量，只输出提案文件：改哪个规则文件、改成什么、依据是哪几个周期、预期改善哪个指标。复盘者不直接改任何东西。
3. **提案送审和批准**：提案作为 kind: plan 走现有评审；评审通过后在看板上等人点头；点头才提交。
4. **前后对比**：每条生效的提案记下生效时的周期号，下一批 10 个周期后自动对比指标。变差的提案在看板上标出来，人决定是否回滚。
5. **第二层（herdsman 自身）**：第 1 到 4 步稳定运行、至少有 3 条提案被证明有效之后，才讨论要不要让复盘也提 herdsman 的代码修改。

### 护栏（不可被 RSI 修改的东西）

这些是手册第 12 部分认定的真正价值，复盘提案**不得触碰**，碰到的提案直接作废：

- evidence 门槛：每条 blocking 必须带 `file:line` 或复现命令。
- 稳定编号和范围冻结。
- 轮次上限、人裁决、止损点本身。
- 度量的定义。不允许「改规则」和「改怎么算好」出现在同一条提案里，防止自我刷分。

另外：

- 任何提案都要人点头才生效，没有自动合并。
- 复盘者和评审方用不同模型，避免自己给自己打分。
- 复盘有成本上限：一次复盘只读最近一批周期，不读全量归档。

### 怎么算成功

- 第 1 步上线后，`precision.md` 和 `escapes.md` 不再需要人手填，数字每个周期自动更新。
- 前 3 条生效的提案里，**至少 1 条**在对比期内让误报率或漏检数变好，且没有让评审耗时明显变长。

### 止损点

第 2 步开始后 **一个月或 3 次复盘**：

- 提案大多是空话或重复（你点头率低于三分之一），就停在第 1 步：保留自动度量，不做复盘提案。
- 发现提案绕过护栏（哪怕被拦下），先修护栏，再决定是否继续。

### 不做

- 不让任何 agent 在无人批准的情况下修改规则或代码。
- 不做在线学习、微调模型。
- 不追求全自动：人始终是批准者。

## 顺序

两件事互不阻塞，但建议：

1. **先做 R2 第 1 步（自动评估）**。它小、低风险，而且 R1 第 3 步需要它来回答「换成 corral，评审质量有没有变差」。
2. 然后 **R1 第 1 步（corral 试验）**。它不碰现有脚本，只回答「corral 能不能替代 herdr」。
3. 之后两条线按各自的分步推进，谁先碰到止损点谁先停。
